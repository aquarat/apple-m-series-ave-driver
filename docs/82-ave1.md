2026-09-26. A plan from host-only static analysis, being run step by step
(docs/53 "A0, S0" and "A2-A6, B1-B2"). **Done: ave1 encodes, and both
encoders run concurrently at full speed (overlay variant=7).** The m1n1
steps (M0/M1) turned out unnecessary: Linux can write the DAPF (docs/84 §3),
iBoot points ave1's RVBAR at ave0's TEXT (A2), and ave1's DATA is a
driver-owned copy of the pristine blob with three tags patched. What is
still open: the PMP vote for ave1 (Asahi's report@22, §1.4) and ave1's own
boot row (§0.1, B3). Tags
follow the repo: **[C]** confirmed from a binary or ADT with the citation
given, **[I]** inferred, **[U]** unknown. ADT = `data/blobs/macos-13.5/adt.bin`
(m1n1 proxyclient parser). The script that produced every §1 number is
`tools/ave1_adt.py` (read-only, ADT-only).

## 0. The findings that change the plan

1. **Boot row for ave1 [C].** macOS 13.5 sends a different row for each
   instance. `AppleAVE2Driver::start` calls `AVE_DevInfo::RetrieveSVEID(provider)`
   at `0xfffffe0008e91620`. That reads ADT `sve-id`, and a missing property
   stores 0 (`str wzr` at `0xfffffe0008ede4cc`). It then passes the value to
   `AVE_Drv::IO_start(provider, idx)` (`0xfffffe0008e91b48`/`b50`), which
   bounds it `< 8` (`0xfffffe0008eedef4`) and hands it to `AVE_HwC::Init` as the
   index (`0xfffffe0008eedff0`). That index is what goes into scratch 1
   (docs/45 §2.1). So ave0 gets instance 0 and ave1 gets instance 1.
   `soc-id` (ave0 `t6000`, ave1 `t6001`) selects kext table rows 13 and 14
   (`0xfffffe0007bc2a38`):
   - ave0 = DevID 14 / DevType 11 / ChipType 8, maxNum 1, **perGroup 1**
   - ave1 = **DevID 15 / DevType 12 / ChipType 9, maxNum 2, perGroup 2**

   Side correction to docs/79 §2 and the comment in `ave_soc.c`: 14/11/8 is
   not "t6000's row borrowed". It is exactly what the kext sends for ave0.
2. **perGroup 2 turns on IOP-to-IOP mailbox routing to the peer [C code,
   I effect].** The firmware's `PlatformIOPIPCManager` constructor (fw
   `0xa9cb0..0xa9ce0`) sets:
   - `perGroup` = row +16
   - `systemID` = index
   - `pos` = index % perGroup
   - `dieID` = index / perGroup

   It computes `systemBaseAddr[i]` from IOBA with a stride of `0xFA000000`
   (fw `0xa9d10..0xa9d8c`, strings `0xce78c`/`0xce7e0`/`0xce7fa`).
   `0xFA000000` is exactly the distance from ave0 to ave1: `0x506000000 −
   0x40c000000`.

   `InitMailboxRoute` (fw `0xaa434`) returns at once when perGroup == 1
   (`0xaa454..0xaa45c`). Otherwise it creates an `RTK_mbi_route` to every
   peer. It is called unconditionally from the `CFlowControllerBase`
   constructor (`0xba90`), which `target_task` constructs at firmware start
   (`0x5a3c` → `0x3c7f4`).

   The kext has `gs_saAVE_{AVC,HEVC}_MultiCoreThreshold_Nyx`
   (`0xfffffe000722f190`, `0xfffffe000723cc48`), and the firmware has
   `*MultiCore` controller paths. So on macOS, ave1 (Nyx) is the multi-core
   partner of ave0.

   **Consequence:** booting ave1 with its macOS row (1, 15) makes its firmware
   reach ave0's ASC mailbox at boot. If ave0 is gated, that is a fabric-hang
   candidate.
3. **The two DAPFs are cross-wired for exactly that reason [C data, I
   meaning].**
   - `dart-ave1`'s filter entry 1, `0x40d050000-0x40dc69000` (r0 `0x31`),
     is ave0's SVE through ASC+`0x469000`.
   - `dart-ave0`'s entry 1, `0x506000000-0x507c6c000`, is ave1's fabric
     through ASC.

   These are the peer windows the mailbox route needs. ave0 has run for 100+
   runs with m1n1 admitting ave1's span and never used it (perGroup 1).
4. **ave1 needs its own firmware DATA [C].** The iBoot tag list inside
   ave0's live DATA (`iboot-window-16m.bin` @ `0xf68000+0x3b00..`) holds:
   - `CpAd` = `0x40d800000`
   - `WrAd` = `0x40dc00000`
   - `IOBA` = `0x40c000000` (DATA VA `0xefbdc`)
   - `SOC_` = `0x6001`

   The firmware forms every MMIO address from `IOBA` (docs/40 version note).
   ave1's firmware must see `CpAd 0x507800000`, `WrAd 0x507c00000` and
   `IOBA 0x506000000`. Pointing ave1 at ave0's DATA, or restoring ave1's DATA
   from `ave-13.5-data-pristine.bin` (whose tags are ave0's), would make
   ave1's core drive **ave0's** hardware. TEXT can be shared: it is
   read-only, fetched physically, and its only iBoot patch is the DVA
   literal `0x1f0000ec000`, which is the same for both [I].
5. **iBoot's ave1 copy has not been seen [U].** The 16 MiB dump from
   `0x10000b28000` holds exactly one AVE TEXT (the three hashed windows match
   only at `0x10000b28000/…ba8000/…c10000`) and one AVE DATA
   (`0x10001a90000`). The rest is other firmware (RTKit ×5, ISP).
   `segment-ranges`/`pre-loaded` are live-ADT-only (docs/09 §1.1), so the
   restore ADT cannot answer.

   macOS 13.5 adopts the image per provider node
   (`AVE_Firmware::RetrieveInfo(IOService*)` `0xfffffe0008ef4968`) and uses
   ave1. That makes a separate iBoot preload for ave1 **likely [I]**, but
   unverified. `UpdateImage` has a non-iBoot branch (`0xfffffe0008ef7764`),
   not analysed.
6. **ave1's ADT `reg[3]` is not ave0's `unk3` shape [C].**
   - ave1's is `0x28e680260 +0x7dc4`: from VENC1_SYS's PS register through
     VENC1_ME1's, covering ANE1_SYS, ANE1_SYS_CPU, MSR1 and more.
   - The driver reads bank 3 at `+0x00..+0x20` as VENC_DMA..ME1
     (`ave_drv.c:653`, `ave_session.c:3459-3463`).
   - So ave1's overlay must use `0x28e688000 +0x24` (ps-regs[17],
     VENC1_DMA..VENC1_ME1).
   - `dts/t6001-ave.dtsi`'s ave1 draft has the ADT literal and needs fixing.

Notes on the table:

- `venc1_*` genpds exist and are off at boot (docs/58 §5) **[C]**.
- The rest of the gate list is virtual (`no_ps`): 549 VENC1-SYS-V,
  550/601/552 SOC VNOM/VMID2/VMAX (id1 35), 603 FAB0-VMAX, 551 MEM-FAST.
  They mirror 456-459/600/602 [C].
- **Fabric path differs [C].** VENC1_SYS hangs off AFNC5_LW0 → AFNC5_LS →
  AFNC5_IOA → AFI. All three AFNC5 are `critical, on` in the ADT. VENC_SYS
  hangs off AVEMSR-V → AFR only. So ave0's `afnc4_ioa` sentinel (`0xc5`,
  "attached by mistake", docs/57, docs/58 §6) has **no ave1 counterpart**. Do
  not add afnc4 to ave1. Whether Linux models `afnc5_*` as venc1_sys parents,
  or as always-on, is **[U]**; A0 answers it.
- `resets = <venc1_sys>`, mirroring ave0.

Why `report@22` cannot be used:

- It sets bit 34 (Asahi's id1−1), not 31.
- `pmp-report.c:105` does `u64 bit_val = 1 << ent->id`, an int shift. For
  34 that is undefined behaviour, likely bit 2 on arm64 [I]. For 31 it
  sign-extends to `0xffffffff80000000` and would RMW bits 31-63 [I].
- Checked against Asahi's `drivers/pmdomain/apple/pmp-report.c` and the
  `t600x-die0.dtsi` entry (branch `asahi`, fetched 2026-09-26).

**Shared state [C ADT, I meaning]:** both AVE0 and AVE1 have soc-device +24
= 13 (`AVEMSR0_AVE` clock domain, docs/75 §11.3), and both VENC*_SYS share
the virtual parent AVEMSR-V. One clock and rail for both encoders. How the
PMP combines two votes is **[U]**.

## 2. Firmware

- **Own copy?** Each instance needs its own DATA (tag list, §0.4) and its own
  RVBAR, which is in its own ASC. The ASC RVBAR is iBoot-locked on ave0
  (docs/31, docs/44). Whether iBoot loads a second copy and locks ave1's
  RVBAR is **[U]** (§0.5). The live ADT answers it: `/arm-io/ave1`
  `segment-ranges` and `pre-loaded`. So does ave1's RVBAR (`0x507850000`,
  read with VENC1 powered).
- **The RVBAR/placement check needs a second set of iboot fields: yes.**
  `ave_fw_check_iboot_placement()` (`ave_fw.c:543`) compares RVBAR with one
  `text_phys` and checks the literal at TEXT+`0x423c`. `fw_map_data` maps DVA
  `0xec000` → `data_phys`. All of it must come from a per-instance row. Unknown
  values must mean refuse (0 = unknown, as the PMP fields already do). Add a
  read-only check that DATA's `CpAd`/`WrAd`/`IOBA` tags equal the instance's
  asc, asc+`0x400000` and axi2af bank starts. ave0 passes it today: live
  values `0x40d800000`/`0x40dc00000`/`0x40c000000` [C].
- **DAPF: yes, ave1 needs m1n1 too.** Linux DAPF writes SError (docs/49).
  Every ave0 run depends on m1n1's programming (docs/50 §5). For ave1, add
  `{"/arm-io/dart-ave1", 3, "/arm-io/ave1"}` to the patch's `dapf_entries[]`
  (`tools/m1n1/0001-…patch` hunk at `dapf_entries`). m1n1's `dapf_init` powers
  the DART's `clock-gates` (518 → VENC1_SYS chain) around the writes
  (`m1n1-src/src/dapf.c:136-160`), and the patch keeps the SError guard. The
  TEXT-append path then prints either "already covered by entry N" or
  "no segment-ranges on /arm-io/ave1". That alone is a readout of §0.5,
  though only on screen.
- **Better readout, proposed:** also have m1n1 copy `/arm-io/ave{0,1}`
  `segment-ranges` (and whether `pre-loaded` exists) into the FDT, e.g.
  `/chosen/asahi,ave1-segment-ranges`. Linux can then read it from
  `/proc/device-tree`. No MMIO, no filming.
- **If iBoot does not preload ave1 (fallback, harder).**
  - Map ave0's TEXT physically: the DAPF on dart-ave1 needs a TEXT entry
    for `0x10000b28000`, so the m1n1 patch would take ave0's segment-ranges
    for dart-ave1.
  - Give ave1 a driver-allocated DATA: pristine blob with the tags rewritten
    to ave1's, mapped at DVA `0xec000` in ave1's domain.
  - This needs RVBAR on ave1 to be writable or pre-set to that TEXT. ave0's
    was not writable (docs/31). The 13.5 kext's `Config` write is skipped
    only for iBoot-loaded types (docs/44 §2.1).
  - Treat this branch as a separate proposal. Do not attempt it until A2
    says RVBAR is unlocked.
- **Boot handshake row: not the same [C], §0.1.**
  - macOS: ave1 = scratch1 1, scratch2 DevID 15, msg4 dev_type 12.
  - **Proposed first:** send ave1 **ave0's row (instance 0, DevID 14,
    DevType 11)**. That gives perGroup 1: no peer routing, and the firmware
    is in the exact configuration ave0 is known-good in. Only the hardware
    behind IOBA differs.
  - Do not mix the two, e.g. (1, 14). With perGroup 1 an index of 1 gives
    `dieID` 1, a die that does not exist [C arithmetic, fw `0xa9ccc`].
  - The macOS row (1, 15, 12) is a late, separate step, only with ave0
    powered and running (§4 B3).
- **What does not change for ave1:**
  - IOP Start sequence: `AVE_IOP_Start_Nyx` `0xfffffe0008f1f110` and
    `_Castor` `0xfffffe0008f1d9e8` have identical immediate and call
    sequences [C, compared].
  - SVE register table: chipType 4-15 → Rhea (docs/45 row 9) [C].
  - DPE tunables: the Castor_6000 set covers DevID 14-16
    (`ave_dpe_tables.h` header) [C per docs/58 §9].

## 5. Risks

1. **Gated-domain fabric hangs.**
   - Any ave1 bank access with `venc1_*` off. The first-access order stays
     ave0's: stage 6 power, stage 7 SVE write, stage 8 ASC read.
   - Any wrong address. Always apply the `0x2_0000_0000` bus offset
     (docs/30). f38 was a read of an address in no block.
   - The ADT's ave1 `reg[3]`, if used verbatim, puts ANE1/MSR1 PS
     registers in the driver's bank-3 reads.
   - ave1 firmware on the macOS row reaching ave0's ASC mailbox while ave0
     is gated (§0.2). Avoided by the (0, 14) row. This also argues for never
     running ave1 on (1, 15) with ave0 unbound.
2. **Shared state between instances.**
   - DARTs, DAPFs, IRQs, PS registers and PTD slots are all separate [C].
   - Shared:
     - the AVEMSR0 clock/rail (soc-device domain 13, docs/75 §11.3) and
       the virtual AVEMSR-V parent;
     - the PMP PS-REQ **word**, 64-bit, holding bits 16 and 31: one RMW
       writer only;
     - the cross-admitting DAPF entries (§0.3): each core can reach the
       other's MMIO;
     - TEXT, possibly, if iBoot shares it [U].
   - A DATA mix-up (§0.4) silently drives the wrong encoder. The DATA-tag
     check in §2 is the guard.
3. **m1n1 change.**
   - A boot loop is recoverable only via macOS/recoveryOS (docs/50 §4).
   - The new boot.bin must be assembled on the current live PMP-DTB image
     (docs/78 §3), not on `boot.bin.ave-dapf`.
   - m1n1 powers VENC1_SYS to program the DAPF. Later genpd cleanup gates
     it, as it does for ave0 (docs/58 §5).
4. **Posted writes.** Every new write on `/soc` must go through a
   resource-based or `ioremap_np` mapping. Plain `ioremap()` writes raised
   f93/f94's SError (docs/53 correction).
5. **Global params hitting both.** `core_reset`, `fw_restore_data`, `pmp_*`
   and `ctl_asc` apply to every instance. They must refuse per instance
   where the row lacks data, not default to ave0's constants.
6. **Unload.** Still one load per boot, no unload. Two instances double the
   teardown surface (docs/63), and it remains untrusted.
