[16](16-encode-surface-set.md), [17](17-aux-engines-pools.md),
[18](18-coded-data-sizing.md), [19](19-infoset-slot-map.md),

This machine runs the 13.5 firmware ([43](43-macos-13.5-firmware.md)).*

**Both columns are first-class results.** The 26.6.2 findings are not wrong or
retracted: they describe the 26.6.2 ABI, and that ABI becomes the relevant one
again if Asahi moves the stub firmware to a newer macOS. The driver should
pick an ABI table by detected firmware version, the way Asahi's DCP driver
handles several firmware versions.

Verdicts:

- **same on both**: positive 13.5 evidence for the same value. Not just "nothing contradicts it".
- **DIFFERS by version**
- **cannot verify on 13.5**: no counterpart found, or not decoded.

Confidence is marked **C** (confirmed: read from an instruction or data, VA cited), **I** (inferred: chain stated) or **U** (unknown).

Addresses:

- 13.5 firmware VAs are image VAs (`__TEXT` vm 0, file `+0x4000`), read with `AVE_MACOS=13.5 python3 tools/disas.py --fw --addr VA`.
- 13.5 kext VAs are kernelcache `__TEXT_EXEC` VAs, read with `AVE_MACOS=13.5 python3 tools/disas.py --kext --addr VA`.
- Where a row cites a bare `0xea…`, `0xeb…`, `0xec…` or `0xf3…` address, it is short for `0xfffffe0008ea…` and so on.
- A string VA in the 13.5 firmware equals its `strings -t x` file offset minus `0x4000`.

Nothing here touched hardware.

## 0. The short version

1. **The per-frame block moved and shrank.**
   - 26.6.2: `AVE_PICMGMT_PARAMS` is `0x5118` bytes at `sCAveCmdAvcProcess+0x12C0` (command `0x63D8`).
   - 13.5: it is **`0xF68` bytes at `sCAveCmdAvcEncode+0x9C8`** (command `0x1940`), and its first `u32` is its own size.
   - Every `AVE_PIC_*` offset differs.
   - 13.5 copies the **whole** command into the controller, not four sub-ranges.
   - **C** (§1).
2. **The rate-control enumeration differs by version, and both readings are correct for their version.**
   - **26.6.2:** wire field `sRC.RCMode` (`Start+0x234`). Constant QP is **3**, CBR is **2**, and the modern framework is gated by `sRC.Feature` bit 31 ([35](35-rc-modes.md)).
   - **13.5:** the wire field is `AVEFWRCSettings.ui32RCFlag` (`AvcInit+0xFF50`), with **0 = AVE_RC_OFF, 1 = AVE_RC_ON, 2 = AVE_RC_FIXQP**. The firmware log string that names that enumeration prints the very field the host writes, with no remap in between.
   - 13.5 has no `RateControl::CreateInstance`, no `ConstantQpRateControl` and no `Check_RCMode`; there is no Feature-bit framework switch.
   - Fixed QPs on 13.5 are `AvcInit+0xFFB4/+0xFFB8/+0xFFBC` (I/P/B).
   - **C**, with one **I** hop (§2).
3. **QP is session-scoped for AVC on both versions**, unless the 13.5 flag is 1 (firmware RC on). **C** (§2.4).
4. **`FrameType` values 0 (I), 1 (P), 2 (B), 3 (IDR) and 5 (UNDECIDED) are the same on both.**
   - 13.5 lets the firmware choose the frame type when the host passes 5.
   - 13.5 rejects 6 in the slice-header builder and accepts 7 as a B type.
   - **C** (§1.3).
5. **The surface layer is structurally different on 13.5.**
   - 30 surface kinds, not 41.
   - `_S_AVE_SurfaceInfoSet` is `0x1EC` bytes of named members, not 35 × 48.
   - There is no index→slot map.
   - The coded-header buffer is `0x23000`, not `0xC000`.
   - At most 20 coded buffers, not 30.
   - The FwIPC surface is `0x700000`, not `0x1400000`.
   - **C** (§4).
6. **Unchanged on both:**
   - the coded-data size formula on the default path;
   - the 64-byte stride rule;
   - the 128-byte recon alignment;
   - the `CodedBufSize > 3·W·H/4` firmware check;
   - Recon, Colocated, MBStats and SrcNeighbor sizes;
   - DPB caps 17/16;
   - chroma divisors.

   **C**.

Why 26.6.2 has so much more (41 surface kinds, MCTF/GGM/DMV engines, devType-dependent sizing, AV1, 21 SoC variants): most of the extra symbol and variant surface is **likely support for newer SoCs and codecs** added after 13.5. **I** — nothing in either binary states it; it follows from the added names (`AV1`, `GGM`, `DMV`, extra `AVE_IOP_Config_*` variants) being absent from 13.5.

### 1.3 `IMG_FRAME_TYPE`

13.5 firmware `AVE_H264_PrepareSliceHeader` (`0x20d44`) switches on the frame type through two 8-entry byte jump tables (`0xcef78`, `0xcef80`; bound `cmp w12,#7` `0x20d6c`, `0x20e08`). The second table's targets:

- 0 → `0x20ff0`
- 1 → `0x21040`
- 2 and 7 → `0x20e38`
- 3 → `0x210d4`
- 4, 5 and 6 → `0x21130`, which logs `"prepareSliceHeaderForFW frametype not recognized"`

| value | 26.6.2 (32 §3) | 13.5 behaviour | 13.5 evidence | verdict | conf |
|---:|---|---|---|---|---|
| 0 | I (non-IDR), slice_type 2 | `[hdr+16] = 2`, frame_num incremented | `0x21004`–`0x2101c` | same on both | C (value), I (field name slice_type) |
| 1 | P, slice_type 0 | `[hdr+16] = 0` | `0x21050` | same on both | C / I |
| 2 | B, slice_type 1 | `[hdr+16] = 1` | `0x20e48` | same on both | C / I |
| 3 | IDR | `[hdr+16] = 2`, `[hdr+34] = 1`, frame_num reset to 0 | `0x210e8`–`0x210f8` | same on both | C / I |
| 5 | UNDECIDED (host sentinel) | the firmware **decides** the frame type itself (`CAVECommonController::GetFrameType` → `CFrameType::FrameType`) and writes the result back to `PICMGMT+0xCAC` | `cmp w28,#5` `0x145d4`; `str w10,[x23,#3244]` `0x23eb8` | DIFFERS (13.5 firmware-side GOP) | C |

### 2.3 13.5: the wire value is the logged enumeration, not an internal flag

This was the trap to rule out: an enumeration in a log string can describe an internal variable rather than the value the host sends. On 13.5 the path from host to log has no remap, hop by hop.

```

      pInfo+0x20  is  AVEFWRCSettings.ui32RCFlag
        AVE_Client_CheckCommonInfo: x20 = arg2 (0xfffffe0008ec9c30);
        ldr w9,[x20,#32] (0xfffffe0008eca308) feeds the asserts
        "ui32RCFlag == AVE_RC_OFF" / "!= AVE_RC_OFF"
        (refs 0xfffffe0008eca360, 0xfffffe0008eca648)                          C
host  memcpy(client+0xD0688, pInfo, 0x680)   AVE_Client_Config 0xfffffe0008ecc1dc-1ec   C
host  memcpy(cmd+0xFF30, client+0xD0688, 0x680)  MakeFwCmd_Start_AVC 0xfffffe0008ea9b40-b54   C
```

**Fixed QP values (13.5):**

- `InitEncodingParameters` builds `sCRCInitParams` on the stack at `sp+0xCA0`:
  - `+12` ← the flag (`0x5d9b0`);
  - `+92` ← `RC+0x84` (`0x5da90`–`0x5da9c`);
  - `+96/+100` ← `RC+0x88/+0x8C` (8-byte load `0x5daa0`–`0x5daac`).
- The same three words also go to the controller at `this+4968/4976` (`0x5cebc`–`0x5cecc`). That is `sCommonParams(+0xA70)+2296/2300/2304`, which the slice-header builder selects by frame type: `{0,3}` → `+2296`, `{1}` → `+2300`, `{2,7}` → `+2304` (`0x20d8c`, `0x20fd8`, `0x20dc0`; table `0xcef78`).
- The host names them: `DEBUG_PrintEncoderSessionHEVC` prints `"QP (I %d P %d B %d)"` from `client+0xD0688+{132,136,140}`. The format is at `0xfffffe00071ecbd5`, the loads at `0xfffffe0008eba188`–`18c`, with base `add x26,x8,#0x688` at `0xfffffe0008eb960c`.

**C.** So, on 13.5:

- **`AvcInit+0xFFB4` = QP I**, **`+0xFFB8` = QP P**, **`+0xFFBC` = QP B** (C host side; command offset I as in §2.3).
- `+0xFF34` = `ui32IdrPeriod` (same print, `[x26,#4]`). C.

**QP is not per-frame on 13.5 for flags 0 and 2.** The only writers of `this+4968/4976` in `CAVCController` are `InitEncodingParameters` (`0x5cec4`, `0x5cecc`) and `SetDefaultParameters` (`0x4680c`, `0x4686c`); no per-frame writer exists (write scan over the whole image). **C.** Whether some other PICMGMT field overrides the QP in hardware programming: **U** (not searched beyond the slice-header path).

`params+0x24`/`+0x28` ← `RC+0x58` clamped to `<51`, and `RC+0x5C` clamped to `1..51` (`0x5d9f0`–`0x5da14`). Likely min/max QP. **I**.

**CBR = 2 on 13.5: cannot verify.** On the 13.5 wire field, value 2 means FIXQP. `CRateControl::AVE_CBR_InsertFiller(..., _E_AVE_RCP, ...)` (`0x43ad0`) exists but takes a different enum type, which was not decoded. **U**.

### 2.5 Resolution of the conflict

The two enumerations are different fields in different ABIs, and neither contradicts the other.

- **26.6.2:** `_E_AVE_RCMode` in `sRC.RCMode`, constant QP = **3** (and CBR = 2).
- **13.5:** `ui32RCFlag` in `AVEFWRCSettings`, `{OFF 0, ON 1, FIXQP 2}`, constant QP = **2**.

Sending 3 on 13.5 would take the "normal RC" arm of `ProcessInit` (`b.ne 0x40188` after `cmp w11,#2`) if a `CRateControl` were built. `InitEncodingParameters` builds one for 3 only via the alternative conditions at `0x5d964`–`0x5d96c`. The slice header then uses the session QPs (flag ≠ 1). Either way, 3 is not the fixed-QP selector on 13.5. **C** (branches).
