# 89. t8103: the M1 (MacBook Air, j313)

The M1 port was done by **Henri Schulz** ([@henriSchulz](https://github.com/henriSchulz))
on the fork's `t8103-port` branch, from this repository at `0e37f6f`, following
docs/79. Merged here on 2026-10-03; their commits are kept in the history. This is
a summary of their write-up and of what changed in the merge. Their bring-up scripts,
on-demand service and m1n1 patches stay on their branch:
<https://github.com/henriSchulz/apple-m-series-ave-driver/tree/t8103-port>
(`t8103/`). Marks as in docs/00; [C] here means confirmed on their machine.

## 1. Status

H.264 through V4L2 works on a MacBook Air M1 (`apple,j313`, t8103), with an Asahi
7.1.13 kernel and macOS 13.5 coprocessor firmware [C]. Not tested there: HEVC,
P010, B frames, more than a few hundred frames per session, system suspend with
the driver loaded (`pm_sleep=2`), two sessions at once, `pipe_diag`, and hung-firmware
recovery.

Load (as the operator, one step per boot for anything new, docs/79 §3):

```sh
make -C driver && make -C test
sudo VARIANT=9 tools/ave-load.sh
```

Needs `/lib/firmware/apple/ave_h13g.bin` (the 13.5 `AppleAVE2FW_H13G.im4p`,
unwrapped) and, to reload in the same boot, `apple/ave-13.5-h13g-data-pristine.bin`
(DATA as iBoot left it, taken before any start with `test/physdump.ko base= size=`,
docs/87 §3 for the method).

## 2. What differs from t6001

| | t6001 (M1 Max) | t8103 (M1) |
|---|---|---|
| ADT nodes | `ave0`, `dart-ave0` (+ `ave1`) | `ave`, `dart-ave` |
| Firmware | `H13C`, TEXT 0xec000, DATA 0x134000 | `H13G`, TEXT 0xcc000, DATA 0x128000; same build tag `AppleAVE2FW-6070.11.1` |
| iBoot placement | TEXT 0x10000b28000, DATA 0x10001a90000 | TEXT 0x8009f4000, DATA 0x8019b0000 (remap 0xf000cc000) on their machine |
| RVBAR | locked | locked, `0x1020008009f4001` |
| DAPF entries in the ADT | window + MMIO | window only (0xf00000000-0xfffffffff) |
| Interrupt controller | AIC2, 4 cells | AIC, 3 cells; AVE 560, DARTs 557 |
| Power domains | me1 without a phandle | me0 and me1 without a phandle, siblings under pipe4 + pipe5 |
| AVE_DPE tunables | `Castor_6000`: 1 CAT + 124 + 123 CAC | `Acis_8103`: no CAT, 1 + 39 CAC |
| Device row (13.5) | 14 / 11 / 8 | 13 / 10 / 7 |
| Handshake message 1 | 7, 0x9bc0, 0x100, 0xc0000 | the same |
| Message 5 client buffer | 0xb4000 | 0xb0000 |
| CPU_STATUS cold / running | 0x2a / 0x2c | the same |
| PMP vote | 2.4-2.6x (t6000 3.0x, docs/87) | none (no t8103 PMP report in Asahi) |

The command ABI, the start sequence (`AVE_IOP_Start_Acis` is instruction for
instruction `_Castor`'s) and the session code needed no change. What did, in the
driver:

- `ave_soc_t8103` (`driver/ave_soc.c`), compatible `apple,t8103-ave`, with the iBoot
  placement read from the live ADT (their m1n1 probe patch exports `/arm-io/ave`
  `segment-ranges` and `pre-loaded` to `/chosen`). **The placement is per machine
  and boot chain**; the driver checks RVBAR and refuses a mismatch.
- `me0_node`: `venc_me0` is powered through a second holder device.
- `ave_soc.dpe`: AVE_DPE tunables are per SoC. `Castor_6000` on the M1 failed
  read-back on 69 entries.
- `ave_soc.pipe_diag`: the session's diagnostic reads of pipe registers use offsets
  known for the t600x DPE only; they are off on t8103 (a read outside a real block
  is a reset, f38).
- `test/ave-overlay-t8103.dts`.

Their usage notes that apply generally: load the encoder only while it is used if
the machine must suspend (the core cannot be suspended running; unload before
suspend, or load with `pm_sleep=1` so a suspend is refused rather than risked),
and pad to the encoder's grid with ffmpeg (`-vf "pad=ceil(iw/64)*64:ceil(ih/16)*16"`),
because ffmpeg's V4L2 wrapper segfaults on a 1080-line input (docs/88 §5).

## 4. Changes in the merge (2026-10-03)

- **Overlay `variant=9`** for t8103. Both ports had taken `variant=8`; t6000 keeps 8.
  Their scripts load `variant=8`: on this tree use 9.
- **The driver programs t8103's DAPF** (`dapf_by_driver = true`), as on t6000, so
  stock m1n1 suffices: the project avoids a custom bootloader where it can.
  Their bring-up used m1n1 for it (their `0002` patch, whose premise "Linux cannot
  write this DAPF" predates docs/84 §3). `ave_dapf_program_instance` now writes the
  ADT MMIO entry only where the SoC has one, so t8103 gets TEXT + window and
  cleared slots, as their m1n1 build programmed. With their m1n1 the driver
  rewrites the same entries (m1n1 sets no lock). **Untested on t8103**: the first
  run on an M1 should be `stop_after=8 dapf_dump=1` on stock m1n1, reading back
  the two entries, before a full load.
- The per-SoC pristine-blob/TEXT-window/STKG refactor existed on both sides; the
  merge keeps the fork's field names (`fw_pristine_sha256`, `data_stkg_off`,
  `text_win`) and the t6000 row uses them, with `dpe = Castor_6000` and
  `pipe_diag = true` (t6000's encoder is t6001's ave0 hardware).
- `test/physdump.c`: their `base=`/`size=` with an allow-list of known firmware
  ranges is kept.

## 5. A second t8103 machine

The row's iBoot placement is their MacBook Air's. On another M1 (e.g. a Mac mini,
`j274`, also H13G per the 13.5 BuildManifest) the TEXT/DATA addresses may differ.
The driver then refuses at the RVBAR check (safe), and the row needs that
machine's placement: from the live ADT (their m1n1 probe patch, read-only, or any
other way of reading `segment-ranges`), or from a cold RAM dump as in docs/87 §3
(add the new ranges to `physdump`'s allow-list first; it accepts only known ones).
Whether that machine needs its own pristine blob is open [I]: iBoot fills ~146
bytes of DATA (STKG, SoC id, coprocessor addresses, tunables), and if the tunables
are per unit, another machine's blob would differ. Compare a cold dump of the new
machine's DATA with the existing blob before reusing it.

**Answered for a Mac mini (j274) in §6:** the placement is the same as the
j313's, but on stock m1n1 iBoot's DATA lies in Linux's RAM, so the driver now
builds DATA itself there, and the blob can be built from the image (§6.3).

## 6. A Mac mini on stock m1n1 (2026-10-04)

A base M1 Mac mini (`apple,j274`, t8103), stock Fedora Asahi m1n1, macOS 13.5
stub firmware. Stage-limited loads by the lead, all safe. Marks as in docs/00.

### 6.1 What the runs showed

- **Up to stage 8 on stock m1n1** [C]: overlay `variant=9`, power domains, the
  SVE idle write, the `Acis_8103` DPE tunables (read back OK) and the
  driver-side DAPF (TEXT `0x8009f4000` r0 `0x11`, the DVA window r0 `0x33`, the
  other slots cleared; read back). So §4's open point is closed: t8103 needs no
  patched m1n1 for the DAPF.
- **Stage 10** [C]: RVBAR `0x1020008009f4001`, TEXT+`0x423c` = `0xf000cc000`:
  the **same placement as the j313** (TEXT `0x8009f4000`, DATA `0x8019b0000`).
  Then `iboot DATA: REFUSING - 0x8019b0000+0x128000 intersects System RAM`.
  On this boot Linux's System RAM was `0x801224000-0x802c27fff`: iBoot's DATA
  lies in memory Linux allocates from (the fork's patched m1n1 kept it out).
  TEXT, `0x8009f4000+0xcc000`, is below that RAM.
- **TEXT is intact** [C]: a read-only `physdump` of TEXT equals `ave_h13g.bin`'s
  `__TEXT` (file `0x4000` + `0xcc000`) byte for byte except the 3-byte iBoot
  literal at `0x423c`.
- **DATA is gone** [C]: the DATA dump after 20 days' uptime holds kernel data
  (sysfs attribute names, linear-map pointers); 0.13 % of the image's non-zero
  bytes match. Both pages that hold iBoot's fills (DATA+`0x0`, DATA+`0x60000`)
  are overwritten.

So on this machine iBoot's DATA can be neither used in place nor restored, and
there is no pristine dump to restore from.

### 6.2 What iBoot writes into DATA

From the pristine blobs we have (H13S, H14G: cold dumps) against their images,
`tools/data_blob_from_image.py validate`:

- The image's `__DATA` holds the RTKit patchbay (`_rtk_patchbay`, symbols
  `__rtk_patch_*`): packed `{4-char code stored byte-reversed, u32 len,
  payload}` records, no alignment, from `STKG` to `IOSZ`. iBoot fills six
  payloads [C]:

  | tag | len | firmware symbol | t6000 (H13S) | t8112 (H14G) | t8103 (H13G) |
  |---|---|---|---|---|---|
  | `STKG` | 8 | `_rtk_stack_guard` | random | random | random (j313 dump: `0x9fe20cd1e87caa00`) |
  | `SOC_` | 4 | `RTK_soc` | `0x6000` | `0x8112` | `0x8103` |
  | `SOCR` | 4 | `RTK_soc_revision` | `0x21` | `0x11` | `0x11` |
  | `CpAd` | 8 | `RTK_cpu_physical_address` | `0x40d800000` | `0x267800000` | `0x267800000` |
  | `WrAd` | 8 | `RTK_cpu_wrapper_physical_address` | `0x40dc00000` | `0x267c00000` | `0x267c00000` |
  | `IOBA` | 8 | `RTK_io_base` | `0x40c000000` | `0` | `0` |
  | payload offsets | | | DATA+`0x3380`.. | DATA+`0x35d8`.. | DATA+`0x3380`, `0x34eb`, `0x34f7`, `0x3503`, `0x3513`, `0x352c` |

- And the table `TUNS`/`TUNZ` point at (`__rtk_platform_asc_tunables_block`,
  DATA+`0x60368`): header `{u8 version 1, u8 3, u8 capacity, u8 count, u32 h}`
  and `capacity` entries `{u32 offset, u64 mask, u64 value}`. The image ships it
  empty (count 0, h `0xffffffff`). H13S: capacity 24, 21 entries, h `0x20`;
  H14G: capacity 36, 23 entries, h `0x10`, and a second table (version 3) that
  iBoot leaves empty [C]. The offsets (`0x51c18`, `0x140020`, `0x140120`,
  `0x140130`..`0x1401a8` in pairs, `0x145010`, `0x1500d0`) look like ASC
  wrapper registers (the firmware applies them; the symbol says "asc
  tunables") [I]. Their values differ between H13S and H14G.
- **Nothing else differs** [C]: H13S 147 bytes, H14G 171 bytes, all inside that
  fill set; the rest of `__DATA` equals the image and the bss is zero (H14G's
  dump covers all of DATA; H13S's dump covered `0xb4000` bytes, the rest is
  zero-padded [I]).
- **Validation** [C]: rebuilt from the image plus the recorded values, both blobs
  are byte-identical to the dumps (same sha256 as pinned in `ave_soc.c`); with
  another STKG they differ in exactly those 8 bytes; the other SoC's tunables, a
  wrong CpAd or no tunables are each rejected (controls).

### 6.3 H13G: which bytes are known

| bytes | value | source | mark |
|---|---|---|---|
| all of `__DATA` outside the fill set | `ave_h13g.bin` | the image (13.5, sha256 `a5cec344…`) | [C] (method validated on H13S, H14G) |
| bss past `0x64000` | zero | as H13S/H14G | [I] |
| `STKG` (8) | any; the tool uses the j313 dump's `0x9fe20cd1e87caa00` | random per boot; a stale value works (docs/51; t6001 reloads, ave1's owned DATA) | [I] |
| `SOC_` (4) | `0x8103` | j313 row | [C] j313, [I] j274 |
| `SOCR` (4) | `0x11` | j313 row (B1) | [C] j313, [I] j274 |
| `CpAd`, `WrAd` (16) | `0x267800000`, `0x267c00000` | j313 row; = the ASC bank in the j274 overlay | [C] |
| `IOBA` (8) | `0` | j313 row | [C] j313, [I] j274 |
| tunables (488 at DATA+`0x60368`) | **unknown** | iBoot's own tables (the IPSW's iBoot images are encrypted; not in the j274, j313, j314s, j314c or j473 ADTs, nor in the M2's 13.5 kernelcache) | [U] |

What the j313 blob says about the tunables, without its bytes: its sha256 is
pinned. Image + the known tags + its STKG + **H13S's table** gives 146 differing
bytes, exactly the count the fork reported, but **not** that sha256. Nor does
H13S's table with any h in 0..0xff (and SOCR 0..0xff), nor with its eight quota
pairs drawn from the four (A, B) pairs H13S and H14G use, ten values of h and ten
of the `0x140120` value (6.5 M candidates, the other entries H13S's). So H13G's
table is probably H13S's shape (same byte count) with other values [I], and its
bytes stay [U] (all of this assumes the j313 dump's bss was zero).

`tools/data_blob_from_image.py build --soc t8103` therefore wants an explicit
source for the 488 tunables bytes:

1. `--dump DATA.bin` (default when given): a read-only `physdump` of DATA from a
   **fresh** boot. The tool takes only iBoot's fill bytes from it, after checking
   that each 16K page holding fills equals the image everywhere else (tag page
   DATA+`0x0`, tunables page DATA+`0x60000`); a page that does not is
   "overwritten" and nothing is taken from it. If the tag page survived, its
   SOC_/CpAd/WrAd/IOBA must equal the table's (else REFUSED) and its SOCR and
   STKG are used. Exact if the tunables page survived [C].
2. The j313 blob from the fork author: pinned already, the driver takes it as it
   is. Exact for H13G if the tunables are per SoC, not per board [I].
3. `--tunables none`: the image's empty table, so the firmware applies no ASC
   tunables and those registers keep their reset values. [I] the firmware
   accepts an empty table (H14G's second table is left empty by iBoot and the M2
   runs); [U] whether anything (speed, a hang) depends on the values.
4. `--tunables h13s`: t6000's table, same H13 ASC generation, same byte count
   as the j313 fills, but known to differ in values [U].

### 6.4 Driver changes

- **`iboot.data_owned` per row, decided at probe.** `AVE_DATA_OWNED` (= true,
  t6001's ave1) as before; new `AVE_DATA_OWNED_IF_RAM` (t8103):
  `ave_fw_data_owned()` asks `region_intersects(data_phys, data_size, System
  RAM)` once per probe and logs `iboot: DATA 0x8019b0000+0x128000 is inside
  System RAM: owned DATA - …` or `is outside System RAM: iBoot's DATA, mapped in
  place`. Outside (the j313 with its m1n1) nothing changes.
- **Owned DATA for any row** (`ave_fw_map_owned_data`). The blob's
  `CpAd`/`WrAd`/`IOBA` records are found by name in its tag list (from
  `data_stkg_off` - 8), not at H13C's fixed `0x3bbb/0x3bcb/0x3be4` (which the
  walk reproduces for H13C). Before anything is built, the row's
  `tag_cpad`/`tag_wrad`/`tag_ioba` must be this instance's: `CpAd` = the ASC
  bank, `WrAd` = `CpAd` + `0x400000`, `IOBA` = the fabric bank or 0; the blob's
  own pair must be one ASC's; TEXT in DRAM must match the row's three TEXT
  windows. The copy is cleaned to the point of coherency before `iommu_map`. For
  t8103 the row's tags equal the blob's, so nothing is patched (logged as "the
  blob's own"); for ave1 the patch is unchanged.
- **Where the core finds it.** As on the j313 and on ave1: DATA at DVA
  `data_dva` = `0xcc000` (= DATA's vmaddr, the low 32 bits of the TEXT literal
  `0xf000cc000`, which the DAPF window `0xf00000000-0xfffffffff` admits and the
  DART translates by its low 32 bits); TEXT is iBoot's, outside RAM, fetched
  physically through the DAPF TEXT entry and left unmapped at DVA `0x9f4000`
  (`fw_map_text=2`). Only DATA's backing pages change.
- **Which blob.** The pinned sha256 (the j313 dump) still passes as it is. A row
  with `iboot.blob_by_image` (t8103) also accepts, **for owned DATA only**, a
  blob that `ave_fw_blob_by_image()` proves to be the image's: the firmware file
  is the image the row's TEXT windows identify; every byte outside the fill set
  (taken from the file's own tag list and `TUNS`/`TUNZ`) equals its `__DATA`, and
  the bss is zero; the tunables header has the image's version/kind/capacity and
  count ≤ capacity; `SOC_`, `CpAd`, `WrAd`, `IOBA` are the row's. What it cannot
  prove is the tunables' values; the tool says where they came from. The
  in-place path (compare with and write over iBoot's live DATA) still requires
  the pinned dump, so an image-built blob can never be written over iBoot's DATA.
- Unchanged: the in-place restore, `ave_fw_data_ran` (owned: CPU_STATUS `0x2a` =
  cold), reload (owned DATA is a fresh copy per probe, freed at unload), the
  t6000/t6001/t8112 rows.
- A userspace harness ran the driver's own `ave_fw_find_tag`/`ave_fw_find_seg`/
  `ave_fw_blob_by_image` on the real H13S and H14G blobs (pass), on tool-built
  H13G blobs (pass), and on negative cases (H13S DATA against the H13G image, a
  wrong SoC id, a corrupted TEXT hash, one flipped `__const` byte, count >
  capacity, a non-zero bss: all refused).

## 7. Mac mini test plan (proposed; the lead runs it)

One variable per run, a fresh boot before each (`tools/lab-reboot.sh`), the
wired netconsole receiver on. Build first: `make -C driver && make -C test`;
`/lib/firmware/apple/ave_h13g.bin` installed. Raw commands below are on the
target; under the harness the same parameters go to
`tools/lab-run.sh NAME "OVERLAY=9 OVERLAY_WAIT=0 HOLD=5" <params>`.

**M1-0, the blob (read-only, no AVE module).** As early as possible after a
fresh boot:

```sh
sudo insmod test/physdump.ko base=0x8019b0000 size=0x128000
sudo cp /sys/kernel/debug/ave_physdump/window.bin data/blobs/j274-data-fresh.bin
sudo rmmod physdump
python3 tools/data_blob_from_image.py dump-check --soc t8103 \
    --image /lib/firmware/apple/ave_h13g.bin data/blobs/j274-data-fresh.bin
```

Expect `tag list page DATA+0x0: SURVIVED|overwritten` and the same for the
tunables page. Then one of:

```sh
# both pages survived (exact):
python3 tools/data_blob_from_image.py build --soc t8103 \
    --image /lib/firmware/apple/ave_h13g.bin --dump data/blobs/j274-data-fresh.bin
# tunables page overwritten: empty table (tags from the dump if their page survived)
python3 tools/data_blob_from_image.py build --soc t8103 \
    --image /lib/firmware/apple/ave_h13g.bin --tunables none [--dump data/blobs/j274-data-fresh.bin]
sudo install -m644 data/blobs/ave-13.5-h13g-data-pristine.bin /lib/firmware/apple/
```

A dump whose tag page survived but disagrees on `SOC_`/`CpAd`/`WrAd`/`IOBA` is
refused: stop and look. Record which source was used; it is the variable for
M1-f.

**M1-a, owned DATA, no core start** (three boots):

|---|---|---|---|
| a1 | `stop_after=10 step_ms=100` | `iboot: DATA 0x8019b0000+0x128000 is inside System RAM: owned DATA - built from the pristine blob in pages the driver owns`; `reload: CPU_STATUS 0x2a: cold`; `iboot: RVBAR base 0x8009f4000, DATA literal 0xf000cc000 - placement as expected`; `… is not the pinned blob; verifying it against the image (owned DATA)`; `pristine by image: apple/ave_h13g.bin __DATA matches outside iBoot's fills; SOC_ 0x8103 SOCR 0x11, N tunable(s) at DATA+0x60368`; `restore: TEXT at 0x8009f4000 matches the 13.5 image over 3 x 0x4000 bytes`; `owned DATA: CpAd at DATA+0x3503 0x267800000 -> 0x267800000 (the blob's own)` (WrAd `+0x3513`, IOBA `+0x352c`); `owned DATA: 0x128000 bytes at phys … -> DVA 0xcc000 (the core reads it at 0xf000cc000)`; `iboot TEXT: leaving DVA 0x9f4000 UNMAPPED`; `stage 10 (…): OK` | any `REFUSING`: the line names the check (blob, TEXT window, tags vs banks); `is outside System RAM` on this boot: the in-place path runs and refuses without the pinned blob, record the RAM map |
