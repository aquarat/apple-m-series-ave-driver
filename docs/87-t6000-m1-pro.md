# 87. t6000: the M1 Pro (MacBookPro18,3, j314s)

2026-09-29. The port from t6001 (M1 Max, j314c) to t6000 (M1 Pro, j314s),
following docs/79. The target is a MacBookPro18,3 on Fedora Asahi Remix 44,
kernel 7.1.13-402.asahi.fc44.aarch64+16k, m1n1 v1.6.1 stock (stage 1 and
stage 2), `asahi,os-fw-version` 13.5, iBoot2 8422.141.2. Marks as in
docs/00: [C] confirmed, [I] inferred, [U] unknown.

## 1. What is the same as t6001's ave0

From the 13.5 IPSW (`UniversalMac_13.5_22G74_Restore.ipsw`),
`DeviceTree.j314sap` against `DeviceTree.j314cap`, dumped with
`tools/adt_dump.py --grep 'ave|pmp'`:

- `/arm-io/ave0`: reg (all five banks), interrupts (1031...), clock-gates,
  power-gates: identical. [C]
- `/arm-io/dart-ave0`: reg[0..3], sids, instance, and
  `filter-data-instance-0` (the 0x1f0 window and the `0x506000000 -
  0x507c6c000` MMIO entry, ave1's span on t6001, although t6000 has no
  ave1): identical. [C]
- The PMGR devices behind ave0's power-gates (VENC-SYS-V, VENC_PIPE4/5,
  VENC_ME0/1, VENC_DMA, VENC-DART...): same ids, psreg and psidx. [C]
- There is no `/arm-io/ave1`. [C]
- The live DT has `venc_sys`, `venc_pipe4`, `venc_pipe5`, `venc_me0`,
  `venc_me1` (same PMGR offsets) and `pmp-venc-sys` (report@10, disabled).
  It has **no `afnc4_ioa`**: t6000's fabric domains are afnc0-3. [C]
- The device row: the driver has always sent t6000's own (14/11/8,
  "Castor"). The DPE tunables applied at stage 7 are "Castor_6000". [C]

## 2. What differs: the firmware variant

The 13.5 BuildManifest gives j314s **AppleAVE2FW_H13S**, not H13C
(docs/43 §1.2). [C] Its layout:

| | H13C (t6001) | H13S (t6000) |
|---|---|---|
| im4p sha256 | `e6efcb2c…359d8f` | `07caebc6…60919c` |
| decoded Mach-O sha256 | `fd615e0b…dc0b2` | `a4271f09…af44f` |
| `__TEXT` | vm 0 +0xec000 | vm 0 **+0xd0000** |
| `__DATA` | vm 0xec000 +0x134000 | vm **0xd0000 +0x128000** |
| bootstrap `adr x0, 0x423c; ldp w0,w1` | at 0x308 | at 0x308 (same) |
| STKG tag value (DATA+) | 0x3a38 | **0x3380** |

## 3. Where iBoot put it on this machine

`test/physdump.ko` (read-only, the same 16 MiB from `0x10000b28000` as on
t6001) on a boot where no AVE driver had ever run, then
`tools/fw_dump_compare.py`:

- H13S `__TEXT` at dump offset 0: 100.0000 % of non-zero bytes, 3446/3447
  unique samples at delta 0; the only difference is the iBoot literal at
  0x423c. The H13C control: 35.6 %, no dominant offset. [C]
- H13S `__DATA` at dump offset **0xf4c000 (phys 0x10001a74000)**: 99.98 %
  of non-zero bytes; `__const`, `__data`, stacks, page tables all 100 %. The
  H13C control there fails on `__const`/`__data`/patchbay. [C]
- TEXT+0x423c holds **0x1f0000d0000** (= 0x1f0 window + DATA vm). [C]
- RVBAR (ASC+0x50000) reads `0x102010000b28001` on the live block, the
  same value as t6001's ave0. [C]

The pristine DATA blob is that dump's DATA (0xb4000 bytes to the window's
end; everything past `filesize` 0x64000 in it is zero) padded with zeros to
0x128000, installed as `apple/ave-13.5-h13s-data-pristine.bin`, sha256
`36d82853…69f8cec7`. That the uncovered bss tail is zero at boot is [I],
as it was for t6001.

## 4. The changes

- `driver/ave_soc.c`: the `ave_soc_t6000` row and set, compatible
  `apple,t6000-ave`. The pristine sha256, the TEXT identity windows and the
  STKG offset moved from `ave_fw.c` into the rows, because they are per
  firmware variant. t6000's windows are 0, 0x80000, 0xcc000 (TEXT ends at
  0xd0000). t6001's rows carry the H13C values unchanged.
- `dapf_by_driver = true`: stock m1n1 does not program dart-ave0's DAPF,
  and the driver can (docs/84 §3), as it does for t6001's ave1. So **no
  m1n1 rebuild is needed** for t6000.
- PMP fields: t6001's values, verified for t6000 (§6).
- `test/ave-overlay-t6000.dts`, `variant=8`: variant=4 with the t6000
  compatible and without `afnc4_ioa`.

Firmware to install: `apple/ave_h13s.bin` (the decoded H13S Mach-O) and the
pristine blob above. Load: `sudo VARIANT=8 tools/ave-load.sh`.

  | size | no vote (t1) | **VMAX + FAB0 vote** | speed-up | t6001 f98/f99 |

## 6. The PMP (performance vote)

`tools/pmp_ptd_map.py` (now tolerant of an SoC without VENC1_SYS) on the
j314s ADT passes C1-C4 and gives, for ave0, exactly t6001's values [C]:
VENC_SYS PS `0x28e5803b0`, soc-device #16 AVE0, DVFS slot 9 (PTD entry 273:
write `0x28e3d0888`, read `0x28e3c1110`), report base `0x28e3c0000`, the
same message encoding (VMax + FAB0-VMAX = `0x2000000300000003`), perf block
9 at `0x28e5d8000`. PMP and PMS_SRAM PS are `0x28e0802d8`/`0x28e0802e0`
(ps-regs[5], psidx 27/28) on both. The live DT has `report@10`
(`pmp-venc-sys`, disabled) at the path `ave-overlay-pmp-venc.dts` targets.
The table row now carries them.

**What is missing is the PMP itself.** `pmp@28e700000` is
`status = "disabled"` in this machine's DT, and `pmp.ko` is present
(`CONFIG_APPLE_PMP=m`) but unbound. As on t6001 (docs/78), m1n1 only starts
it when the DTB is built with `-DAPPLE_USE_PMP`. Doing that on this machine
means rebuilding `t6000-j314s.dtb` from the kernel's own source with that
flag, and splicing it into `/boot/efi/m1n1/boot.bin`. Per docs/78 the flag
also moves disp0/dispext0, ISP **and AVD** onto `pmp_report_*` power domains.
On a machine that relies on AVD for decoding, that makes it a separate,
operator-approved change. Without the PMP, `pmp_report=1` and
`pmp_vote=` warn and are ignored, and the encoder runs at the boot clock
(t6001: 1080p ~70 fps, 4K ~19 fps; with the vote ~170/~48).

## 7. An APPLE_USE_PMP stage 2 for j314s (built, not installed)

Built on the target from the running kernel's own source
(`kernel-7.1.13-402.asahi.fc44.src.rpm`: `linux-7.1.13.tar.xz` plus
`patch-7.1-redhat.patch` and `Makefile.rhelver`, `.config` from
`kernel-aarch64-16k-fedora.config`, the kernel's own `dtc`) [C]:

- Stock `make apple/t6000-j314s.dtb` is **byte-identical** to the installed
  `/boot/dtb/apple/t6000-j314s.dtb` (`1737a97c…acef2f`), which validates
  the build.
- With `#define APPLE_USE_PMP` at the top of `t6000-j314s.dts`:
  `d0595d94…ca182`. The preprocessed source differs only in the six
  `#ifdef APPLE_USE_PMP` blocks of `t600x-common.dtsi`, `t600x-die0.dtsi`
  and `t600x-dieX.dtsi`. The phandle-resolved DTB diff shows the same
  thing: the `pmp` alias, and power-domains moved to PMP report entries
  for `avd@286000000` (report@11), `isp@384000000` (report@b, first
  domain), `dcp@38bc00000` (report@c), `dcp@289c00000` (report@d) and
  `dcp@28cc00000` (report@e). All five entries are enabled in this DT.
  Everything else is phandle renumbering.
- `boot.bin` reassembled the way `update-m1n1` does it (`m1n1.bin`, the
  `t6*.dtb t81*.dtb` of this kernel, gzip `u-boot-nodtb.bin`, the
  `/etc/m1n1.conf` options) is **byte-identical** to the ESP's
  (`6522d07f…3e634e`, 5019314 bytes). The PMP candidate (`134f8b0b…e7d20`,
  5019430 bytes) differs from it only in the j314s DTB at offset 1425424;
  the prefix and the suffix were checked with `cmp`.
- m1n1 v1.6.1 `dt_set_pmp` bails (no boot) if the ADT lacks `/chosen`
  `board-id` or `dram-vendor-id`, or `/arm-io/pmp/iop-pmp-nub`. The j314s
  restore ADT has all three (66 nub properties, `dram-capacity` too). The
  live ADT is a superset [I].
- `pmp.ko` (`CONFIG_APPLE_PMP=m`) aliases `apple,t6000-pmp-v2`.

Artefacts in `data/blobs/m1n1-j314s/` (git-ignored): `boot.pmp.bin`,
`esp-boot.bin` (copy of the live one), both DTBs. Restore script:
`tools/m1n1/restore-pre-pmp-j314s.sh` (tested on a simulated ESP directory).

Install, **not yet done** (needs the operator; it is this machine's
bootloader, and AVD is in use):

```sh
B=data/blobs/m1n1-j314s
sudo cp -p /boot/efi/m1n1/boot.bin /boot/efi/m1n1/boot.bin.pre-pmp && sync
sudo sha256sum /boot/efi/m1n1/boot.bin.pre-pmp     # 6522d07f...3e634e
sudo cp tools/m1n1/restore-pre-pmp-j314s.sh /boot/efi/m1n1/ && sync
sudo cp $B/boot.pmp.bin /boot/efi/m1n1/boot.bin.new && sync
sudo mv -f /boot/efi/m1n1/boot.bin.new /boot/efi/m1n1/boot.bin && sync
sudo sha256sum /boot/efi/m1n1/boot.bin             # 134f8b0b...e7d20
# optional: echo 'M1N1_UPDATE_DISABLED=1' | sudo tee -a /etc/sysconfig/update-m1n1
#   otherwise the next kernel/m1n1/u-boot package update rebuilds boot.bin
#   with stock DTBs, which silently turns the PMP off again (safe, not lost)
# reboot; then check: pmp@28e700000 status okay, pmp module bound,
#   "PMP started" in the journal, AVD still decoding (on report@11)
```

Undo: `sudo sh /boot/efi/m1n1/restore-pre-pmp-j314s.sh`, then reboot. If
Linux does not boot, run it from macOS/recoveryOS (tools/m1n1/RESTORE-README.txt).
The ESP's partition UUID is machine-specific and not recorded here:
`lsblk -o NAME,LABEL,PARTUUID` shows it.
