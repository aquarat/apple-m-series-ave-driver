# Boot, transport and IPC on macOS 13.5 vs 26.6.2

Docs [03](03-protocol.md), [08](08-ipc-transport.md), [09](09-firmware-load.md)
(minus the RVBAR / `AVE_IOP::Config` / fetch parts, which belong to
[44](44-reset-fetch-path.md)), [10](10-power.md),
[11](11-interrupts-bringup.md), [28](28-ave-init-order.md),
[33](33-firmware-logging.md), [34](34-boot-handshake.md),
[36](36-ipc-implementation.md) and [40](40-firmware-io-base.md) were read from
**macOS 26.6.2** (25G83). The coprocessor firmware this machine runs is
**macOS 13.5** (22G74), proven byte-for-byte in
[43](43-macos-13.5-firmware.md). This document re-reads every concrete boot,
transport and IPC claim of those docs against the 13.5 firmware image and the
13.5 `AppleAVE2` kext, and records **both** values.

Neither column supersedes the other. 26.6.2 stays authoritative for 26.6.2
firmware, which Asahi may move the stub to later; 13.5 is what runs today. A
driver should carry both ABIs and select one by the firmware version it detects
(the approach Asahi's DCP driver takes). The companion for commands and session
setup is [46](46-abi-13.5-commands-session.md).

Verdicts: **same on both** (positive 13.5 evidence of the same value and
meaning — not "nothing contradicts it"), **DIFFERS by version**, **cannot
verify on 13.5** (what was tried is stated). Confidence per row: **C**
confirmed (read from an instruction or table, VA given), **I** inferred (chain
stated in §2), **U** unknown.

Addresses: 13.5 firmware VAs are image VAs (`__TEXT` VA 0 = file `0x4000`,
`__DATA` VA `0xec000` = file `0xf0000`). 13.5 kext VAs are kernelcache VAs; the
leading `0xfffffe0008` / `0xfffffe0007` is dropped in the table where it would
only repeat (`f11d08` means `0xfffffe0008f11d08`, `bc2a38` means
`0xfffffe0007bc2a38`). Reproduce any row with
`AVE_MACOS=13.5 python3 tools/disas.py --fw|--kext --addr VA -n LEN`.
Static analysis only; nothing here was run on hardware.

| `ave0` (`soc-id t6000`) DevID / DevType / ChipType | 11 / 9 / 6 | **14 / 11 / 8** | **DIFFERS** — C both sides |
| IOP variant for `ave0` | `_Castor` | `_Castor` (same writes) | same on both — C |
| Channels offered by the firmware | 2 (`IO`, `IO_T2H`), 992/993 slots | **7** (`TERMINAL`, `IO`, `DEBUG`, `BUF_H2T`, `BUF_T2H`, `SHAREDMALLOC`, `IO_T2H`), `IO`/`IO_T2H` 32 slots | **DIFFERS** — C |
| `FwIPC` surface | index 31, `0x1400000` | index 24, **`0x700000`** | **DIFFERS** — C |
| Time-base write to scratch 4/5 before message 2 | yes | **no** (neither side) | **DIFFERS** — C |
| Firmware log | shared `FwLog` ring whose address is in the boot block | **no `FwLog`, no `AVE_Log_*`**; firmware logs over the `TERMINAL` IPC channel | **DIFFERS** — C (routing I) |
| Ring algorithm, slot `0x40`, phase bit, descriptor stride `0x100` and field offsets | [36](36-ipc-implementation.md) §4–6 | identical | same on both — C |

The single change most likely to decide whether a 13.5 firmware sends message
1 is the **pre-start scratch contents**: on 13.5 the host writes
`scratch0 = 0x08042006`, `scratch1 = instance index`, `scratch2 = DevID`
(14 for `ave0`), and nothing else. The firmware reads scratch 0 as its standalone
test exactly as on 26.6.2 (`0xa5f94`), so the magic alone already selects the
host-driven path; a 26.6.2-style IOVA in scratch 1/2 is not dereferenced by the
13.5 firmware, but its low byte is later used as a DevID lookup whose miss is a
NULL dereference (`0xa9cb4`, §2.1). Message 1 itself is sent before that lookup
(§2.1), so a wrong scratch 2 should not block message 1 but would crash the
firmware after the ready flag. **Inferred** from the instruction order; not
observed.

That 26.6.2 carries 21 IOP variants, 34 DevIDs and SoCs up to `t8152` while
13.5 has 15 / 28 and stops at `t8130` plausibly explains the DevID and
ChipType renumbering: new SoCs were inserted into the enums. **Inferred.** The
channel set runs the other way (13.5 has more), so that difference is not
explained by SoC growth; 26.6.2 appears to have pruned channels. **Inferred.**

## 2. Notes on the rows that differ or could not be verified

### 2.1 Pre-start scratch registers (rows 25–30)

The 13.5 `StartUpIOP` main path before `AVE_IOP::Start` is, completely:

```
f11ae4  AVE_Firmware::UpdateImage()
f11b74  AVE_IPC ctor ; f11b90 AVE_IPC::Init(devInfo, surfMgr, idx, sve, fw)
f11d08  SetIOPFlag(0)                         scratch0 = 0x08042006
f12004  WriteScratch(1, HwC[+0x40])           instance index
f1211c  WriteScratch(2, GetDevID())           14 for ave0
f1224c  AVE_IOP::Config(GetBaseAddr())        conditional, see [44]
f122dc  AVE_IOP::Start()
f123fc  RecvIOPMsg(&m0, &m1, &m2, &m3)        message 1
```

**Confirmed.** On the firmware, `CPlatformEnvironment` reads all three
registers up front (`0xa5f90`, `0xa5fb0`, `0xa5fc8`), stores the standalone
flag from scratch 0, and in the host-driven branch runs the whole handshake
(`RealChannelCreateTarget`, `0xa6258`) **before** it uses scratch 1/2. It uses
them once, as bytes, at `0xa63c8..0xa63d0`:
`PlatformIOPIPCManager(devID = Read(2) & 0xff, index = Read(1) & 0xff, base)`.
That constructor calls `_AVE_FindByDevID(devID)` (`0xa9cb0`), which returns
NULL for anything outside 1..28 (`0xaab98..0xaab9c`), and immediately loads
`[x0, #16]` (`0xa9cb4`). **Confirmed** instruction sequence; that a wrong DevID
therefore faults the firmware after the ready flag is **inferred** (the NULL
load is unconditional; what RTKit does on that fault was not followed). It then
derives a group index and remainder from the instance index and the table's
per-group count (`0xa9cc8..0xa9ce0`); the meaning of those is **unknown**.

`ave0`'s instance index is `AVE_HwC::Init`'s index argument (`f10190`). That
it is 0 for `ave0` is **inferred** from 26.6.2's reading ([34](34-boot-handshake.md)
§4 footnote); it was not traced to the ADT on 13.5.

### 2.2 DevID, DevType, ChipType renumbering (rows 2–7, 55)

Both 13.5 binaries carry the same 28-row table (kext `bc2a38`, firmware
`0xee4d0`). Rows relevant here:

| `soc-id` | DevID | DevType | ChipType | maxNum | maxPerGroup | IOP variant |
|---|---:|---:|---:|---:|---:|---|
| `t8101` | 12 | 9 | 7 | 1 | 1 | Acis |
| `t8103` | 13 | 10 | 7 | 1 | 1 | Acis |
| **`t6000`** | **14** | **11** | **8** | 1 | 1 | **Castor** |
| **`t6001`** | **15** | **12** | **9** | 2 | 2 | **Nyx** |
| `t6002` | 16 | 13 | 9 | 4 | 2 | Nyx |

The number comes from the entry's `+0x20` word formatted `"%s%d"` with the
`"t"` string (`edebe8..edec10`; `0x1770` = 6000). **Confirmed.** The 13.5 table
starts at `t8006`, `t8301`, `t8310` and ends at `t8130`; the 26.6.2 table drops
`t8006`/`t8301`/`t8015`/`t8028` and adds eight later SoCs, which shifts every
index. **Confirmed** for the table contents; the reason is **inferred**.

### 2.3 Firmware logging (rows 37, 71, 94–97)

On 13.5 neither the `_S_AVE_Fw_Cfg` block nor the `FwLog` surface exists, so
there is no address to give the firmware and no ring to read. Instrumentation
goes through RTKit's `CLogger`. The host-driven branch of `CPlatformEnvironment`
binds `CLoggerInterProcessor` to the `TERMINAL` channel (`0xa636c..0xa63a0`),
and the 13.5 kext dispatches channel 4 = `TERMINAL` to `ProcessIntr_Log`
(`f0d790`). **Confirmed** at both ends. That `CLogger::Print` output reaches the
`TERMINAL` ring, and in what framing, is **inferred**: `CLoggerInterProcessor`'s
print path (`0xa46f4`) and the host's `UnidirectionalReceive64` (`f4535c`) were
not read. It is the only firmware log path found on 13.5, and it needs the
whole handshake to have completed.

Consequence: the 26.6.2 observability plan in [33](33-firmware-logging.md) §10
(read the ring with no IPC) has no 13.5 counterpart. The protocol-free liveness
probes that remain on 13.5 are the scratch registers (message 1 in scratch
0..3, the literal `0x100` in scratch 2) and scratch 7 once the flow controller
exists.

### 2.4 Channel table (rows 40–41, 73–80, 92–93)

Seven descriptors, in firmware order, base = the 64-byte-aligned channel-block
address:

| i | name | host id | `+0x40` dir → host type | `+0x44` bit | `+0x48` slots | slot array |
|---:|---|---:|---|---:|---:|---|
| 0 | `TERMINAL` | 4 | 2 → 2 | 0 | 512 | `base+0x700` |
| 1 | `IO` | 1 | 0 → 1 | 1 | 32 | `base+0x8700` |
| 2 | `DEBUG` | 5 | 0 → 1 | 1 | 8 | `base+0x8f00` |
| 3 | `BUF_H2T` | 6 | 0 → 1 | 2 | 1 | `base+0x9100` |
| 4 | `BUF_T2H` | 7 | 1 → 0 | 3 | 1 | `base+0x9140` |
| 5 | `SHAREDMALLOC` | 3 | 1 → 0 | 3 | 8 | `base+0x9180` |
| 6 | `IO_T2H` | 2 | 1 → 0 | 3 | 32 | `base+0x9380` |

Arithmetic check: `0x700 + 512×0x40 = 0x8700`, `+32×0x40 = 0x8f00`,
`+8×0x40 = 0x9100`, `+0x40 = 0x9140`, `+0x40 = 0x9180`, `+8×0x40 = 0x9380`,
`+32×0x40 = 0x9b80`; plus `0x40` of slop gives exactly the `0x9BC0` in message 1
(`0xa5bdc`) — the same `0x40` remainder [36](36-ipc-implementation.md) found on
26.6.2. **Confirmed.**

What it means for a host (**inferred** from row 84's init rule): the host is
the initiator on every dir-0 channel and writes `slot[0] = 1` into `IO`,
`DEBUG` and `BUF_H2T`, not only `IO`. Doorbell bits are shared on 13.5 — bit 1
by `IO` and `DEBUG`, bit 3 by `BUF_T2H`, `SHAREDMALLOC` and `IO_T2H` — so one
status bit does not identify one channel, which is why Apple's loop calls
`CheckChIntr` and then drains every channel whose bit is set.

### 2.5 `FwIPC` size (rows 66–67)

13.5 creates `FwIPC` at `0x700000` (7 MiB). The firmware only requires the size
and IOVA to be 16 KiB aligned (row 47), and the driver's current 20 MiB would
satisfy that. Whether the firmware has a *maximum* was not searched for.
**Unknown.** Matching Apple's 7 MiB on 13.5 is the low-risk choice.

### 2.6 Rows marked "cannot verify on 13.5"

* **31** — 26.6.2 raises power inside `StartUpIOP`; on 13.5 it does not, and
  where `AVE_DPM` is called instead was not traced.
* **81** — the abort-on-unknown-name path was not re-read; the firmware's names
  are all in the host table, so it is not reachable.
* **89** — the type-2 ring used by `TERMINAL` was not disassembled on either
  version.
* **102** — the 13.5 PMGR dependency tables have a different shape and were not
  decoded. The Linux genpd tree does not come from these tables, so no driver
  constant depends on it.

## 3. The 13.5 boot sequence, for a driver

Constants from §1; every one has a 13.5 VA in the table.

```c
/* before Start (IRQ not requested) */
scratch[0] = 0x08042006;
scratch[1] = instance;            /* 0 for ave0 (inferred)          */
scratch[2] = 14;                  /* DevID t6000 on 13.5            */
/* Config per docs/44; Start: 0x400808<-1, 0x400044<-0,
 * 0x400400<-0x10000, 0x400044<-0x10                                */

recv(&nch, &chsz, &ver, &heap);   /* expect 7, 0x9BC0, 0x100, 0xC0000 */
/* reject nch outside 1..8, chsz == 0, ver != 0x100                 */
send(fwipc_iova_lo, fwipc_iova_hi, 0x700000, 0);   /* no scratch 4/5 */
recv(&lo, &hi, NULL, NULL);       fw_base = lo | (u64)hi << 32;
if (heap) heap_surface = alloc_16k_aligned(heap);
chmem = fwipc_alloc(chsz), 64-byte aligned, zeroed;
info  = fwipc_alloc(0x50), zeroed:
        +0x08 = FW_ADDR(chmem); +0x1C = heap IOVA (u64, unaligned);
        +0x24 = heap size; +0x28 = 11 /* DevType */; +0x4C = 0;
send(FW_ADDR(info) lo, hi, 0, 0);
recv(&dlo, &dhi, &cbuf, NULL);    /* reject cbuf > 0x100000; expect 0xB4000 */
/* FW_TO_CPU(desc) must == chmem; bind all 7 descriptors (§2.4)     */
scratch[3] = 0x08042006; poll until 0, 20000 x 100 us;
/* now request IRQ index 0; loop ch 1..7 on each interrupt          */
```
