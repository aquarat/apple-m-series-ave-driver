# 98. t6002: the M1 Ultra (Mac Studio, j375d)

2026-10-04. The port to the M1 Ultra, from host-only static analysis: the
j375d restore ADT and H13D firmware from the macOS 13.5 IPSW, and a
decompiled live device tree and genpd summary that the lead read from a
j375d running Fedora Asahi Remix 44 (kernel 7.1.13-402.asahi.fc44
16K, stock m1n1 and DTB, `asahi,os-fw-version` 13.5). §9 is the bring-up
plan. **Status (same day): works on hardware, all four encoders; §11 has the
runs and benchmarks.** Marks as in docs/00:
[C] confirmed, [I] inferred, [U] unknown.

## 0. Summary

- t6002 is two t6001 dies, and its four encoders are t6001's two, twice.
  ave0 and ave1 (die 0) are t6001's ave0 and ave1 byte for byte in the ADT.
  ave2 and ave3 (die 1) are the same blocks with 0x20_0000_0000 added to
  every CPU address, die 1's AIC, and die 1's PMGR [C, §2].
- The firmware is **AppleAVE2FW_H13D**, which is not H13C. It is H13C
  rebuilt, though: same layout, same 1390 symbols, same patchbay. The
  `SetTunable` table has three more AVE_DPE pipe tunables [C, §3]. The
  driver needs H13D's own TEXT identity hashes and nothing else
  firmware-specific.
- What static analysis cannot give is **where iBoot put the firmware** on
  this machine, whether it preloaded ave1-ave3 as well, and the pristine
  DATA blob. The live ADT has all three. m1n1 already exposes it to Linux as
  a reserved-memory node, and **U0 reads it with a read-only module**
  (§4, a finding that holds for every m1n1-booted Mac). The t6002 rows take
  their placement from a block that `tools/t6002_placement.py` generates.
  Until the block is filled in, the driver refuses at probe, before it
  touches any register.
- **No PMP vote.** The stock DT has the PMP disabled, and turning it on
  means a different DTB in m1n1's stage 2, which is a boot-path change.
  Die 1 has no VENC report entries in Asahi's DT at all [C, §7]. Each
  encoder therefore runs at the boot clock. On t6001 without the PMP that
  was ~14 ms per 1080p frame and ~54 ms per 4K frame [I for t6002]. There
  are four encoders, so four streams at once should give ~4x that.

## 2. The four encoders [C]

From `DeviceTree.j375dap` (13.5 IPSW, `data/derived/adt-j375d-ave.txt`).
The `/arm-io` ranges map bus 0 to CPU 0x2_0000_0000 and bus 0x20_0000_0000
to CPU 0x22_0000_0000, so CPU = bus + 0x2_0000_0000 on both dies. Die 0's
nodes are the j314c ADT's, value for value (diffed).

¹ As on t6001 (docs/82 §0.6), the ADT's ave1 reg[3] is 0x8e680260
+0x7dc4, the whole VENC1_SYS..VENC1_ME1 PS span. The overlay uses ps-regs[17],
VENC1_DMA..ME1, because the driver reads bank 3 at +0..+0x20.

How each row was checked against the live DT:
- `soc@2200000000` has `ranges = <0x02 0x00 0x22 0x00 0x04 0x00 …>`, so a
  die-1 child at `<0x4 0x0d100000>` is CPU 0x240d100000.
- Die 1's AVD, `<0x00 0x01 0x3f3 0x04>`, shows how Asahi's AIC2 takes the
  die: in the second cell.
- The labels `venc_sys_die1` … `venc1_me1_die1` are present under
  `soc@2200000000/power-management@28e580000` and `@28e680000`. In the
  genpd summary, all 24 VENC domains are off.
- There is no node at any of these addresses yet.

The two DAPF peer windows are cross-wired per die. ave0 admits ave1's span
and ave1 admits ave0's, as on t6001 (docs/82 §0.3). ave2 admits ave3's
span, but from ave3's SVE (0x2507050000), not from its axi2af: ave0's
entry starts at ave1's axi2af, so the two dies differ here. The driver
writes the ADT's entries as they are.

## 3. The firmware: H13D [C]

The 13.5 `BuildManifest.plist` maps `j375dap` → `Firmware/ave/AppleAVE2FW_H13D.im4p`
(docs/43 §1.2; `j375cap`, the M1 Max Studio, is H13C).

| | H13C (t6001) | H13D (t6002) |
|---|---|---|
| im4p sha256 | `e6efcb2c…359d8f` | `1dbd8708…2d9426a` (1465833 bytes, the same size) |
| decoded Mach-O sha256 | `fd615e0b…dc0b2` | `dfa0dac9620f6ebcf1a2531309d572b2108f3b8eadad6909cb162b79355251ee` (1465808 bytes) |
| `__TEXT` / `__DATA` | vm 0 +0xec000 / 0xec000 +0x134000, file 0xf0000 +0x64000 | identical |
| `_rtk_patchbay`, `_rtk_tunables` | DATA+0x3a30, +0x60368 | identical addresses and bytes |
| version | `AppleAVE2FW-6070.11.1`, RTKit-2062.141.1 | identical |

The symbol tables (1390 entries each) have the same names. One function
changed size: `CAVECommonController::SetTunable`, 672 → 588 bytes. The
table it applies to AVE_DPE+0x1100000 has 235 entries instead of 232; the
three new ones are pipe tunables at +0x30740, +0x30744 and +0x30748
(`mask 4, 0x8fff0000/0x07ff07ff/0x07ff07ff`). The second table is the same.
After that function everything moves by -0x54. All 1056 bytes in which the
file-backed DATA differs are pointers that moved by -0x54/-0x50/-0x20 with
it, plus the build timestamp. So, for the driver:
- STKG (DATA+0x3a38), the CpAd/WrAd/IOBA tag offsets (+0x3bbb/+0x3bcb/+0x3be4)
  and docs/51's iBoot-filled ranges are H13C's;
- the TEXT identity windows are H13D's own. `ave_soc.c` holds them, computed
  from the image the same way H13C's and H13S's were, and checked by
  recomputing those two against their rows:
  `99ae8315…`, `feb9d43d…`, `344a2519…` at 0, 0x80000, 0xe8000. iBoot's
  literal at 0x423c lies outside all three;
- the boot bootstrap is unchanged. It sets TCR.IPS from the core's own
  ID_AA64MMFR0, so the 38-bit die-1 addresses are a question for the
  hardware, not for the image.

Get it like the other variants. Only the H13D Mach-O goes to
`/lib/firmware`:

```sh
./.venv/bin/python tools/fetch_firmware.py --board j375d --variant H13D --outdir data/blobs/macos-13.5-j375d \
  --url https://updates.cdn-apple.com/2023SummerFCS/fullrestores/032-69606/D3E05CDF-E105-434C-A4A1-4E3DC7668DD0/UniversalMac_13.5_22G74_Restore.ipsw
./.venv/bin/pyimg4 im4p extract -i data/blobs/macos-13.5-j375d/Firmware/ave/AppleAVE2FW_H13D.im4p \
  -o data/blobs/macos-13.5-j375d/ave_h13d.bin          # sha256 dfa0dac9...51ee
sudo install -m644 data/blobs/macos-13.5-j375d/ave_h13d.bin /lib/firmware/apple/ave_h13d.bin
```

## 4. Placement: the live ADT, from Linux

iBoot's `segment-ranges` and `pre-loaded` exist only in the **live** ADT.
docs/42 §3.1 and docs/82 §0.5 took the live ADT to be invisible from
Linux, which is why the M1 Pro needed a 16 MiB dump and a search
(docs/87 §3), the M2 three carve-outs (docs/90 §3.1), and the M1 an m1n1
proxy session (docs/89). That is no longer true. Since v1.6.1 m1n1's
`dt_setup_mtd_phram()` (`src/kboot.c`) publishes the ADT that iBoot handed
it as a reserved-memory node: compatible `"phram"`, label `"adt"`, size
`ALIGN_UP(devtree_size, 16K)` [C]. The j375d DT has it,
`flash@10003a04000 { label = "adt"; compatible = "phram"; reg = <0x100
0x3a04000 0 0xa4000>; }`, and so does an M1 Pro. Fedora's kernel has no
phram driver, so nothing exposes it, but it is reserved DRAM that Linux
never writes. `physdump.ko adt=1` copies it, and `seg=N` copies the
segments it names for `/arm-io/aveN`. Neither touches a register.

There is nothing to guess from. Linux's RAM on the j375d starts at
0x10001d78000 (t6001: 0x1000218c000). The asc-firmware carve-outs are SIO
only, at 0x10000d90000 and 0x10001b88000, because there is no ISP. So the
memory below RAM is laid out differently from any machine measured so far.
A wrong `text_phys` would be refused at stage 10 (RVBAR check). A wrong
`data_phys` with the right TEXT would hand the core foreign memory, so the
placement has to be read.

`tools/t6002_placement.py` turns the live ADT plus cold dumps into the
block (§9 U0). Its checks:
- every `aveN` `reg[0]` equals the restore ADT's;
- ave0 has one TEXT (iova 0, 0xec000) and one DATA (iova 0xec000,
  0x134000);
- the TEXT dump is the H13D image byte for byte, except the literal, which
  must be 0x1f0000ec000;
- the DATA dump is the image outside docs/51's iBoot ranges and zero
  beyond the file-backed 0x64000. That is what makes it cold;
- the DATA tags CpAd/WrAd/IOBA are that encoder's own banks.

It writes the pristine blob, which is that DATA, as docs/87 §3 did. Its
`--selftest` (synthetic ADT and dumps built from the image, including a
warm-DATA negative control) passes. The parser was also run on the real
restore ADT, where it finds the four nodes and their filters and no
segments, as expected.

## 5. ave1-ave3: preloaded or owned [I]

On t6001 iBoot preloaded ave0 only, and pointed ave1's RVBAR at ave0's TEXT.
ave1 then runs on a driver-owned copy of the pristine DATA with its own
three tags (docs/82, A2-A6). The ADT says nothing about t6002 until U0.
The block and the tool handle both cases:
- **if iBoot preloaded aveN**, its row uses its own TEXT and DATA, and its
  own pristine blob `apple/ave-13.5-h13d-aveN-data-pristine.bin`;
- **otherwise** its TEXT is ave0's and its DATA is owned. The tags are
  ave1 0x507800000/0x507c00000/0x506000000, ave2
  0x240d800000/0x240dc00000/0x240c000000, and ave3
  0x2507800000/0x2507c00000/0x2506000000. "TEXT is ave0's" is the t6001
  pattern; the stage-10 RVBAR check is what confirms it, and it refuses
  otherwise.

**Die 1's firmware addresses its block globally [I, strong].** The
firmware forms every MMIO address from IOBA, and its peers at IOBA +
0xFA000000·i (docs/82 §0.2). The ADT's DAPF filter for dart-ave2, the
window through which that core reaches its peer, admits
0x2507050000-0x2507c6c000. That is ave3's block at its global die-1
address (CPU = bus + 0x2_0000_0000). The same arithmetic from a die-local
IOBA (0x40c000000) would land on 0x506000000, which that filter does not
admit. So the owned die-1 rows carry global tags. If iBoot did preload a
die-1 DATA, U0 also reads its tags directly. If they are die 0's numbers,
the tool withholds the owned die-1 rows (TEXT 0, refused at probe) rather
than give them the wrong ones.

## 6. Device row, DPE tunables, DAPF

- Device row: macOS would send each encoder its own row (ave0 14/11/8,
  ave1 15/12/9, ave2/ave3 16/13/9 with perGroup > 1: Nyx/t6002, docs/45).
  That turns on the firmware's routing to its peers. The driver sends
  14/11/8 to every encoder, which is what t6001 runs both encoders on
  (docs/82 §0.1, §2): each core stands alone.
- The DPE tunables `Castor_6000` cover DevID 14-16 (`ave_dpe_tables.h`).
  H13D's three extra tunables are applied by the firmware itself.
- DAPF: the driver programs it (`dapf_by_driver`). Entries: iBoot TEXT
  r0 0x11, the 0x1f0 window 0x33, the ADT's MMIO entry 0x31. This is the
  stock-m1n1 path proven on t6000 and t6001's ave1 (docs/84 §3), with no
  m1n1 change.

## 7. The PMP [C]

- `pmp@28e700000` is `status = "disabled"` in the live j375d DT. Fedora's
  DTBs are built without `APPLE_USE_PMP` (docs/78), so the PMP does not
  run and the vote is not available. With `pmp_report=1`/`pmp_vote=` the
  driver warns and ignores them.
- `pmp_report@28e3c0000` has `report@10` `pmp-venc-sys` and `report@22`
  `pmp-venc1`, both disabled. Its `*_die1` entries are display only, and
  there is **no die-1 VENC entry**.
- `tools/pmp_ptd_map.py` on the j375d ADT passes C1-C4. It gives ave0
  exactly t6001's values (VENC_SYS PS 0x28e5803b0, soc-device #16 AVE0,
  DVFS slot 9: write 0x28e3d0888, read 0x28e3c1110, VMax + FAB0 =
  0x2000000300000003) and ave1 t6001's ave1 values (#31, slot 18). The
  t6002 ave0 row carries the former, for the day the PMP runs.
- Turning the PMP on means a different DTB in m1n1's stage 2. That needs
  `APPLE_USE_PMP` or an equivalent fixup, validated for j375d (m1n1 bails
  and the machine does not boot if the ADT lacks what `dt_set_pmp` reads).
  Separately, `update-m1n1` rebuilds stage 2 from stock DTBs on every
  update. Both are boot-path changes, and are out of scope here. U5 is
  therefore N/A.

## 8. Risks, by hang risk

1. **Die 1 at all (U3b, U3c): the highest.** No AVE has run on a second
   die. Every address was checked against the ADT and the live DT, and the
   dtbos were applied to the live FDT offline. Still untested:
   - the core reaching 0x24xx_xxxx addresses (TCR.IPS from the core's
     PARange; global addressing is [I], §5);
   - a die-1 core fetching ave0's TEXT across the die boundary, if RVBAR
     points there.

   apple-dart binds die 1's DART nodes as soon as the overlay is applied,
   which is the step that hung t6001 once (docs/24). The domains are the
   right ones by label, and die 1's AVD does the same thing with its
   `apple,t8110-dart`.
2. **The first power and MMIO on this SoC (U1a).** venc_sys on, SVE idle
   write, ASC read, DAPF writes (non-posted). These are t6001's blocks at
   t6001's addresses, with only the H13D DATA differing, so low.
3. **The first firmware start (U1b).** H13D is H13C plus three tunables.
   A firmware hang is not a machine hang: the driver times out, and the
   core resets on close (docs/84). Low.
4. **Owned DATA for ave1-ave3 (U3).** This is t6001's ave1 mechanism,
   proven there. The tags for die 1 are [I] (§5), and the tool's check
   applies if iBoot gives evidence. Moderate on die 1, low on die 0.
5. **Reload (U4).** The proven reset-and-restore path. It needs the H13D
   pristine blob (U0); without it a reload is refused. Low.
6. **No risk:** U0 (DRAM reads of reserved memory and the firmware's own
   carve-outs, no module touching the encoder).

The machine is in use, so:
- a hang shows as an instant stop, with no oops or panic, followed by a
  PMU watchdog reset ("1 boot error(s) and 0 panic(s)", docs/24). Local
  logs lose their tail (AGENTS.md), and only a netconsole receiver on
  another host says where it died;
- the modules are loaded by hand from the build tree, so a reset comes back
  with no AVE loaded, and nothing loads at boot;
- **do not install the fleet's AVE service, or anything that loads
  `apple_ave` at boot, until U4 has passed.** A probe that hangs at boot
  hangs every boot.

## 9. Hardware plan

From the repo root on the target, as the lead, one variable per run,
recorded in docs/53. "Fresh boot" means no AVE module has been loaded since
boot. `D` is a private scratch directory **outside git**: the ADT and dumps
are machine-specific and Apple-derived. Load the V4L2 core first
(`sudo modprobe -a videodev v4l2-mem2mem videobuf2-common videobuf2-v4l2
videobuf2-dma-contig`; `tools/ave-load.sh` does it). Wired netconsole to a
receiver before U1a (AGENTS.md).

### U0: read-only (no reboot, no hang risk)

```sh
tr '\0' '\n' </proc/device-tree/compatible | head -2        # apple,j375d apple,t6002
tr -d '\0' </proc/device-tree/chosen/asahi,os-fw-version; echo   # 13.5
cat /proc/device-tree/reserved-memory/flash@*/label         # one is "adt"
sudo grep -E '^venc' /sys/kernel/debug/pm_genpd/pm_genpd_summary   # 24 lines, all off-0
lsmod | grep -E 'apple_ave|ave_overlay'                     # nothing
ls /proc/device-tree/soc@200000000 | grep -c video-encoder  # 0
make -C driver && make -C test                              # kernel-16k-devel, dtc, python3
sha256sum /lib/firmware/apple/ave_h13d.bin                  # dfa0dac9...51ee (§3)
sudo insmod test/physdump.ko adt=1 && sudo cp /sys/kernel/debug/ave_physdump/adt.bin $D/ && sudo rmmod physdump
python3 tools/t6002_placement.py --adt $D/adt.bin            # which aveN have segments
sudo insmod test/physdump.ko seg=0 && sudo cp /sys/kernel/debug/ave_physdump/ave0-*.bin $D/ && sudo rmmod physdump
# and seg=1/2/3 for each encoder the previous step showed segments for
python3 tools/t6002_placement.py --adt $D/adt.bin --dumps $D --apply driver/ave_soc.c
sudo install -m644 $D/ave-13.5-h13d-data-pristine.bin /lib/firmware/apple/   # (+ aveN blobs if any)
make -C driver
```

Pass:
- `physdump: /arm-io/ave0 pre-loaded = …`, two segments (TEXT 0xec000 at
  iova 0, DATA 0x134000 at iova 0xec000), not intersecting System RAM;
- the tool prints `0 byte(s) differ besides the literal; literal
  0x1f0000ec000`, `0 byte(s) differ outside iBoot's ranges, 0 non-zero
  byte(s) past the file-backed 0x64000`, CpAd/WrAd/IOBA `0x40d800000/0x40dc00000/0x40c000000:
  this encoder`, and a pristine sha256;
- `git diff driver/ave_soc.c` touches only the block.

Record in docs/53 what the ADT says about ave1-ave3, their segments or
none, and the dart-ave filters as iBoot left them.

A "no":
- no `adt` phram node: m1n1 is older than 1.6.1. Stop.
- ave0 without segments: iBoot did not preload. Stop; the port needs a
  different approach.
- TEXT/DATA not H13D, or DATA not cold: wrong image, or a core has already
  run this boot. Reboot and repeat U0's dumps before any load.

### U1a: power, MMIO, DAPF and placement on ave0, core not started (reboot after)

```sh
sudo insmod test/ave-overlay.ko variant=11
sudo insmod driver/apple-ave.ko stop_after=10 dapf_dump=1
```

Expected, in order:
- `ave-overlay: variant=11 - t6002 (M1 Ultra) ave0`, the sentinels
  resolved (`aic -> phandle 0x23`, `venc_sys -> 0x2d`, `venc_pipe5 -> 0xd7`,
  `venc_me0 -> 0xd9`, `venc_pipe4 -> 0xd8`), `applied`;
- apple-dart binding `40d040000.iommu` and `40d030000.iommu`;
- `probe: SoC row t6002 (encoder 0)`, `stage 1..10: OK`, `attached 4 power
  domain(s)`, `me1: venc_me1 powered`, `dpe: Castor_6000 tunables applied …
  read back OK`, `ASC CPU_STATUS = 0x0000002a` (cold);
- `dapf: programming t6002's DAPF (m1n1 does not)`, then 16 slot writes
  read back (TEXT r0 0x11, window 0x33, `0x506000000-0x507c6c000` 0x31);
- `RVBAR (ASC+0x50000) = …`, base = the block's ave0 TEXT;
  `iboot: RVBAR base …, DATA literal 0x1f0000ec000 - placement as
  expected`; `iboot DATA: DVA 0xec000 -> phys <ave0 DATA> +0x134000 RW,
  verified`; no DART fault.

## 12. Several encoders behind any node (`open_balance`)

2026-10-04, static work and a build; **not yet run on hardware** (the test
plan is at the end of this section).

**The problem.** Each encoder is its own platform device with its own node
(`apple-ave-enc`, `apple-ave1-enc` .. `apple-ave3-enc`), and an encoder runs
one stream: a second context's STREAMON gets -EBUSY (`av->owner`, docs/68
§7). ffmpeg's `*_v4l2m2m` encoders and GStreamer's v4l2 elements choose the
node themselves: ffmpeg walks `/dev`, opens each node and keeps the first
m2m encoder with the right formats, so every ffmpeg lands on the same node.
Measured on the Ultra: four concurrent `ffmpeg -c:v hevc_v4l2m2m`, all on
the same node; three failed with "VIDIOC_STREAMON failed on capture
context".

**The behaviour.** `open()` of any node binds the new context to an
encoder:

1. the node's own, if no context is bound to it and it is usable (not
   hung, no re-probe queued): exactly the old behaviour;
2. else the usable encoder with no bound context and the lowest index,
   among those *compatible* with the node's: same firmware image and ABI,
   same HEVC support, same two-reference support for each codec, and so
   the same formats, sizes, controls and ranges;
3. else the node's own, as before: the later STREAMON fails with -EBUSY
   while another stream runs there (-EIO if it is hung).

A move is logged on the opened node's device, rate-limited:
`v4l2: apple-ave-enc busy; this open uses apple-ave2-enc` ("hung" instead
of "busy" when the node's own encoder is unusable rather than taken).
Opening `apple-ave2-enc` while encoder 2 is free still gets encoder 2.

**The parameter.** `open_balance` (bool, default 1, 0444). `open_balance=0`
is the old behaviour: every context on its node's encoder. Use it, or make
sure the other encoders are free, for any test that must run on one
particular encoder.

**Busy means "a context is bound", not "a stream runs".** Any open file
counts, an idle one or a probe too. That is what makes ffmpeg's pattern
work: ffmpeg opens the node to probe it, closes it, and opens it again for
the stream (`v4l2_probe_driver`, then `v4l2_configure_contexts`, in
`libavcodec/v4l2_m2m.c`). The encoder is chosen at every open, and the
choice and its count are one critical section, so concurrent opens get
different encoders while any is free.

### What belongs to the node and what to the encoder

A context keeps two pointers: `ctx->nav`, the node it was opened on, and
`ctx->av`, the encoder it is bound to (equal unless it moved).

| | from | why |
|---|---|---|
| `video_device`, `v4l2_fh`, events, priority | node | the file is the node's; the V4L2 core holds that vdev |
| vfd lock **and the vb2 queue lock** | node (`nav->dev_mutex`) | the core runs queue ioctls under the queue lock and the rest (S_FMT, S_SELECTION, ENCODER_CMD, controls) under the vfd lock. They were one mutex before, and the handlers rely on it: S_FMT tests `vb2_is_busy`, S_SELECTION `vb2_is_streaming`, ENCODER_CMD changes the m2m drain state that STREAMOFF also changes. The *encoder's* mutex as queue lock would split one file's ioctls across two locks. Contexts never relied on `dev_mutex` against each other: that is `hw_mutex` and `owner` |
| `release()`'s lock around `v4l2_m2m_ctx_release` | node | it is the queue lock |
| QUERYCAP (`card`, `bus_info`) | node | clients match bus_info to the device they opened; the encoders a context can move between have the same `card` |
| m2m context (`v4l2_m2m_ctx_init`), `device_run`, `job_finish` | encoder | v4l2-mem2mem runs one job at a time per m2m_dev, and the job runs on that encoder |
| work queue, `hw_mutex`, `owner`, session start/stop, `fw_hung`, `pm_lost` | encoder | |
| vb2 `dev` (allocation, dma-buf import) | encoder | the IOVA must be on the bound encoder's DART |
| control ranges (`hevc`, `two_refs`), ENUM_FMT, ENUM_FRAMESIZES, the H.264 two-reference clamp | encoder | identical between compatible encoders anyway; taken from `ctx->av` so that is never an assumption |
| PM quiesce/resume, recovery | encoder | they act on the encoder's m2m_dev and owner; a context is suspended with the encoder it runs on |

After open, nothing else reached the encoder through the node: before this
change only QUERYCAP, ENUM_FMT, ENUM_FRAMESIZES and open used the node's
`drvdata`, and every other handler, queue op, m2m op, the controls, the PM
paths and the debugfs files already went through `ctx->av` or the
`ave_device`.

### Lifetime

A module-global list holds the registered encoders, under a leaf mutex
that also guards two counters per `ave_v4l2`: `ctxs` (contexts bound to the
encoder, which the choice looks at) and `users` (those, plus the files open
on its node wherever they are bound). An encoder joins the list once it is
fully registered and leaves it first thing in `ave_v4l2_unregister`.

- **Module unload** cannot happen with a file open: the node's cdev holds a
  reference to the module, and every encoder is in the same module. With a
  file open `rmmod` says "in use", as before.
- **The re-probe after a hang** (docs/84 §5) frees the `ave_v4l2`, so it
  waits for `users` to reach 0, which now counts files opened on *other*
  nodes and bound here, and files opened on *this* node and bound
  elsewhere (the node's `video_device` lives in the `ave_v4l2`). The last
  release schedules it, under the list lock. A hung or recovering encoder
  is never a target, and the PM paths set `fw_hung` before they call
  `ave_v4l2_idle()`, which takes the same lock, so no open binds to an
  encoder whose re-probe is already decided.
- A side effect: a node whose encoder hung is not re-probed while a file
  opened on it runs on another encoder, only at that file's close. Before,
  that open would have failed at STREAMON instead.

### Races and what remains

- **Concurrent opens** cannot pick the same free encoder: choice and count
  are one critical section.
- **A transient open holds an encoder.** Anything that has a node open for
  a moment (another ffmpeg's probe, `v4l2-ctl --list-devices`, a GStreamer
  device monitor) makes that encoder busy for that moment. A real open
  that comes while such an open holds the last free encoder falls through
  to case 3 and its STREAMON fails, although an encoder frees up a moment
  later. With four ffmpegs on four encoders that needs one ffmpeg's probe
  to overlap another's real open while the other two encoders are taken:
  narrow, but possible. With five, which one fails is down to timing.
  Fixing it means choosing at STREAMON, which means moving a context's
  queues and buffers between m2m devices and DARTs after REQBUFS: not done.
- **An idle open counts.** A client that keeps a node open without
  streaming (a GStreamer pipeline left in READY) keeps that encoder from
  the others. The price of choosing at open.
- **Not fixed, older than this:** unbinding a device through sysfs (any
  `ave_remove` with files open) frees the `ave_v4l2` under the open files.
  `ave_v4l2_unregister` now warns when it happens. With `open_balance` the
  files at risk include those bound from other nodes. For a later change:
  `suppress_bind_attrs`, or a kref on `ave_v4l2` dropped from the
  `video_device`'s release callback.
- **Not fixed, older than this:** the last release schedules the re-probe
  before the V4L2 core's final `video_put()` of the node. The re-probe runs
  from a work item, so later in practice, but nothing orders the two.
