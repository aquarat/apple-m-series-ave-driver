# Incident: hard SoC hang during the first probe attempt

**2026-09-07, M1 Max (j314c), Fedora Asahi 7.1.6-400.**

The machine went down hard while attempting the first driver probe. No data was
lost and nothing persists, but the risk assessment that led to the attempt was
wrong, and the way it was wrong is worth recording.

## What happened

1. `apple-ave.ko` was built and loaded. It bound to nothing, as expected — the
   base device tree has no `apple,ave` node.
2. To give it something to bind to, a device-tree overlay was written adding
   **both** an `ave0` node and a `dart_ave0` IOMMU node, plus a helper module to
   apply it (this kernel has `CONFIG_OF_OVERLAY=y` but no configfs interface).
3. The first apply was rejected — `dtc -@` emits a `__symbols__` node the live
   tree does not have (`init_overlay_changeset() failed, ret = -22`).
4. The overlay was rebuilt without `-@` and re-applied. Shortly after, the
   machine stopped.

## Evidence

- **PMU record: `1 boot error(s) and 0 panic(s)`.** Zero panics is the important
  part: this was not a kernel software fault. It was an unclean hard stop.
- No oops, no `BUG:`, no stack trace, no pstore entry.
- The last journal line is an ordinary `sudo` session opening and closing
  normally, then nothing.

That signature — instant stop, nothing logged, no panic, PMU boot error — is
what an **SoC-level hang** looks like: a CPU wedged with interrupts off, reset
by the PMU watchdog.

## Most likely cause

Device probe is asynchronous. `insmod` returning cleanly and the shell session
closing does **not** mean the overlay was safe; the probe ran afterwards.

The overlay created a **DART** node. Unlike the AVE driver — which only
`ioremap`s and touches no registers before failing at firmware adoption —
`apple-dart` *does* program its registers on probe. The overlay gave that DART
`power-domains = <0x1d>` (`venc_sys`), chosen by inference from the ADT, not
from evidence. If that domain is wrong or insufficient, `apple-dart` writes to
an unpowered or unclocked block.

**On Apple silicon, an access to an unpowered register block hangs the fabric.**
There is no fault, no abort, no panic — the CPU stops and the PMU eventually
resets the machine. That matches the evidence exactly.

This is a hypothesis consistent with all available evidence, not a proven root
cause. Proving it requires a serial console, which is the whole point below.

## Where the risk assessment went wrong

[23-empirical-bringup.md](23-empirical-bringup.md) argued the blast radius was
small: the DART contains bad addresses, iBoot owns the firmware, so the worst
case is a wedged coprocessor needing a reboot. **That reasoning was sound for
the coprocessor and was then wrongly extended to the whole experiment.**

The specific errors:

1. **The DART is the safety net, so standing up a new DART is not a contained
   act.** The containment argument assumed a *working, correctly powered* DART.
   Creating one from an inferred power-domain reference is a different and much
   larger risk than anything the AVE driver itself does.
2. **"Probe will fail cleanly at firmware adoption" only covered `apple-ave`.**
   The overlay bound two drivers. The other one was never risk-assessed.
3. **Asynchronous probe was not accounted for.** A clean `insmod` return was
   treated as evidence the step had completed safely.
4. **A daily-driver laptop with no serial console was the wrong venue.** A hang
   with no console is a black box: it destroys exactly the information needed to
   understand it.

## What this changes

**Do not apply device-tree overlays that create new hardware nodes on this
machine without an m1n1 hypervisor serial console attached.** That console is
not a nicety for this kind of work — it is the difference between a diagnosis
and a reboot with no information. Earlier docs demoted tracing off the critical
path on the grounds that static analysis had superseded it; that was right about
*analysis* and wrong about *bring-up*. The second machine is needed after all,
just later than originally thought.

Revised order for a first probe attempt:

1. Attach a second machine running the m1n1 hypervisor, so a hang is observable
   and the last MMIO access before it is visible.
2. Bring up **only** the AVE node. Do not create a DART node — either confirm
   `dart-ave0` is emitted by m1n1 first, or run without an IOMMU initially.
3. Verify the power-domain references against the PMGR, rather than inferring
   which domain a block belongs to.
4. Expect probe to fail at firmware adoption, and treat reaching that failure as
   the success criterion.

## State afterwards

Nothing persists. The modules were `insmod`-ed, never installed to
`/lib/modules`; there are no `modules-load.d` or `modprobe.d` entries, no
`.dtbo` in `/boot`, and device-tree overlays are RAM-only. A reboot fully clears
it, which is what happened.

The test scaffolding is kept in `test/` with this document referenced from it,
so the next person does not repeat the attempt unaware.
