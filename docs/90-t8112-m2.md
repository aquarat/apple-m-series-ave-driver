# 90. t8112: the M2 (Mac mini, j473)

*The first port outside the M1 family. Two things are new on the M2: the
encoder fetches its firmware through a DART of the newer `t8110` design, and
its source reader needs the picture size in a Process field the M1 firmware
reads only for compressed input. Both are handled in the driver. No m1n1
change and no kernel change: stock m1n1, stock Fedora Asahi kernel.*

2026-10-03, on a Mac mini (M2, `Mac14,3`, `j473`), Fedora Asahi Remix 44,
kernel `7.1.13` (16K pages), macOS 13.5 stub firmware.

## Status

Works, from a clean boot and after an unload and reload in the same boot,
with byte-identical output both times:

| test (`tools/v4l2-test.sh`) | result |
|---|---|
| H.264 720p, v4l2-ctl, fixed QP, 120 frames | 120/120, Y 44.22 dB |
| H.264 720p, ffmpeg `h264_v4l2m2m`, 8 Mb/s, 120 frames | 120/120, Y 53.01 dB |
| H.264 1920x1080 (1088 buffer, 1080 crop), v4l2-ctl | 60/60, Y 44.69 dB |
| H.264 3840x2160, v4l2-ctl | 60/60, Y 44.70 dB |
| HEVC Main 720p, v4l2-ctl, 60 frames | 60/60, Y 44.3 dB mean (I 45.5, P >= 44.0) |
| HEVC Main10 720p (P010), v4l2-ctl, 60 frames | 60/60, Y 55.6 dB mean (10-bit scale) |

Per-frame time (`enc:` line), no PMP vote: 720p 3.2 ms, 1080p 6.4 ms
(~157 fps), 2160p 23.7 ms (~42 fps). The M1 Pro needed 7.9 / 15.5 /
55.5 ms without a vote and 2.9 / 5.2 ms (720p / 1088p) with one (docs/87 §5).

HEVC is graded frame by frame against the source (the target's
`ffmpeg-free` has no HEVC decoder). Note for whoever grades HEVC with
ffmpeg's `psnr` filter on a raw `.h265`: with `setpts=N` on both inputs the
framesync compared every decoded frame with source frame 0 here and reported
25 dB for a correct stream. Decode to raw first (docs/88 §5 says the same for
PSNR in general).

There is **no speed vote on the M2, and none is needed** (§9): the encoder
already runs at its full speed without the PMP. Enabling the PMP, the
M1 Pro's route to a 3x speed-up, makes the M2's encoder ~1.5x *slower*.
Not done: B-frames (untested here) and the larger M2 dies (t6020/t6021),
which are a separate port.

## What differs from the M1 family

| | t8103 (M1), docs/89 | t8112 (M2) |
|---|---|---|
| ADT nodes | `ave`, `dart-ave` | the same |
| Firmware | `H13G`, TEXT 0xcc000, DATA 0x128000 | `H14G`, TEXT 0xd0000, DATA 0x128000 (file-backed 0x64000), same build tag `AppleAVE2FW-6070.11.1`, symbols present |
| `dart-ave` | `dart,t8020` | **`dart,t8110`**, `vm-base` 0x800000000, `sid` 0 and 15, `remap 1`, no `dapf-instance-0` |
| Firmware fetch | physical, admitted by a DAPF entry | **through the CPUDART** (translated) |
| RVBAR | `0x1020008009f4001` (TEXT phys) | **`0x800000001`**: `vm-base`, a DART address |
| iBoot placement | TEXT 0x8009f4000, DATA 0x8019b0000 | TEXT phys 0x8008e0000 (DVA 0x800000000), DATA phys 0x800e88000 (DVA 0x8000d0000) |
| DATA literal (TEXT+0x423c) | 0xf000cc000 | 0x8000d0000 |
| DAPF | window entry; driver programs TEXT (docs/84 §3) | all 16 entries empty; nothing to program |
| iBoot tags in DATA | `IOBA` filled | `SOC_` 0x8112, `SOCR` 0x11, `CpAd` 0x267800000, `WrAd` 0x267c00000; **`IOBA`/`IOSZ` 0**, and H14G has no code that reads them (§3.3) |
| Interrupts | AIC, AVE 560, DARTs 557 | AIC2, 3 cells, AVE **692**, DARTs **689** |
| MMIO, DART, SMMU, DAPF, PMGR addresses | | the same as t8103 |
| Power domains | me0/me1 without a phandle | the same; `venc_dma` is the parent of pipe4/pipe5 |
| AVE_DPE tunables | `Acis_8103` | **`Atlas_8112`**: 1 CAT + 124 + 123 CAC |
| Device row (13.5) | 13 / 10 / 7 | **18 / 15 / 10** |
| Handshake msg 1 / msg 5 | 7, 0x9bc0, 0x100, 0xc0000 / 0xb0000 | the same |
| CPU_STATUS cold / running | 0x2a / 0x2c | the same |
| Process PICMGMT +0x964/+0x968 | read for compressed input only | **read for linear input too: the source size** (§5) |
| Speed vote | PMP dashboard, ~3x (t6000) | VENC votes in the AP `SOC` domain, already at its top; the PMP slows the encoder (§9) |

## 2. AVE_DPE tunables (`Atlas_8112`)

`gs_sAVE_DPE_CfgSet_Atlas_8112` at `0xfffffe0007bd6d38` in the M2's
kernelcache: 1 CAT default, 124 CAC default, 123 CAC 8-bit entries
(`driver/ave_dpe_tables.h`). The same decoder, run on the same kernelcache,
reproduces the existing `Castor_6000` and `Acis_8103` tables byte for byte
(the controls). Atlas differs from Castor in 65 of 124 default and 73 of 123
8-bit entries, so reusing a neighbour's set would not have been right. On the
machine: `Atlas_8112 tunables applied (1+124+123) and enabled, read back OK`.

## 3. The firmware is fetched through the CPUDART

### 3.1 Placement

A stage-limited probe (`stop_after=10 dapf_dump=1`) stopped at the
placement check and printed `RVBAR = 0x800000001`. On the M1s the RVBAR
base is TEXT's physical address. 0x800000000 is the start of DRAM on this
machine, but it is also `dart-ave`'s `vm-base`, and the core cannot fetch
from there physically without an admitting DAPF entry, of which there are
none. The physical memory below Linux's first RAM page (0x801120000) that no
reserved-memory node claims was read with `test/physdump.ko` (three
carve-outs, now in its allow-list), and compared with the H14G image:

- **TEXT** at phys **0x8008e0000**: identical to the image except 2 bytes,
  the DATA literal at TEXT+0x423c, which iBoot set to **0x8000d0000**
  (= `vm-base` + 0xd0000, the image's DATA VA).
- **DATA** at phys **0x800e88000**: the image's file-backed DATA with the
  iBoot tags filled in; the rest (to 0x128000) zero.

So the core runs at DVA 0x800000000 and finds DATA at DVA 0x8000d0000, both
translated by the CPUDART. The CPUDART's registers say the same: iBoot left a
static window at CPUDART+0x400..0x410 (0x3, 0x34, 0x00800000, 0x008008e0):
DVA 0x800000000, 0x34 16K pages (= 0xd0000, TEXT's size), PA 0x8008e0000.

The row records that as `iboot.translated = true` with `text_dva`
0x800000000 and `data_dva` 0x8000d0000. The driver then checks the RVBAR
against `text_dva` instead of `text_phys`, maps TEXT read-only and DATA
read-write at those DVAs in Linux's domain (as on the M1s, where the DVAs are
small), and never leaves TEXT unmapped (`fw_map_text` is forced to 1).

### 3.2 The pristine DATA blob

DATA was dumped before any start of the core in that boot, so the dump is the
pristine copy (docs/51): `apple/ave-13.5-h14g-data-pristine.bin`, 0x128000
bytes, sha256 `fe2d5ec1b2f92798e5847e0fc066fc95dbbdd5e3526651ba00216b45b7839f3d`.
`STKG` is at DATA+0x35d8. To rebuild it on another j473: load `physdump.ko`
with `base=0x800a20000 size=0x608000` before the encoder has ever started in
that boot, and take 0x128000 bytes at offset 0x468000. Same-boot reloads
restore it (§4) and were tested.

### 3.3 IOBA is not used by H14G

On t6001 an `IOBA` of 0 silenced the firmware (docs/40). Here iBoot leaves
`IOBA` and `IOSZ` at 0, the M2's kernelcache has no `IOBA` string at all, and
H14G has no code that addresses the tag (its tag list is at VA 0xd377c; no
`adrp`/`add` or `ldr` forms any address in 0xd3770-0xd37a0 except one stack
setup). The value is not needed on this firmware.

## 4. The `t8110` DART

The register layout differs from the t8020/t6000 one (from Linux's
`apple-dart.c`): TCR at 0x1000 + 4·sid (TRANSLATE bit 0, BYPASS_DART bit 1,
BYPASS_DAPF bit 2), one TTBR per stream at 0x1400 + 4·sid (VALID bit 0),
ERROR at 0x100 (stream 27:20, code 14:0), ERROR_ADDR at 0x170/0x174,
TLB_CMD at 0x80, ENABLE_STREAMS at 0xc00, 16K of registers. `ave_dapf.c` now
reads and writes TCR/TTBR/ERROR through a per-family layout
(`ave_dart_t8020`, `ave_dart_t8110`; the row's `dart_t8110` picks it), and
skips the t8020-only registers (PARAMS, CONFIG, REMAP, DAPF_LOCK) on t8110.
A t8110 DAPF entry has a fifth word at +0x20 (`r20`, m1n1
`dapf_init_t8110a`), read in dumps and written when programming. On this
machine all 16 entries are empty and the row does not program any.

Two things the reload path (docs/84 §4) needed on t8110, both seen on the
machine:

1. The block reset clears **DART1's global stream enables**
   (`ENABLE_STREAMS` 0x0 afterwards) and the VALID bit of its TTBRs. The
   restore now writes the enables back to all-ones first, as Linux's
   `apple_dart_hw_reset` does.
2. A rewritten TTBR reads back VALID but is **not used until that stream's
   TLB is flushed**: the first reload ended in `translation fault ... stream:0
   (NO TTBR FOR IOVA)` from a TTBR that read back right. The restore now
   flushes each stream it writes (`TLB_CMD` FLUSH_SID, as
   `apple_dart_t8110_hw_tlb_command`).

The core-reset check that the DAPF admits the TEXT fetch (docs/49) does not
apply to a translated fetch; on t8112 it only requires that the reset left
the DAPF unchanged.

## 5. The zero picture, and PICMGMT +0x964

### 5.1 The symptom

With the firmware up, every encode completed with valid streams, correct
headers and plausible timing, and decoded to an all-black picture: luma 0
everywhere, H.264 PSNR 5 dB, 4 KB for 120 frames. An I_PCM frame
(`session_ipcm=1`) carried 0x01 in every sample (0 clamped to the legal
minimum), so the source reader delivered zeros. The driver's own source
(`session_frame=1`, debugfs `input_luma.bin`) was intact in memory, the
reconstruction buffer stayed all zero, and no DART reported a fault.

### 5.2 Ruled out, on the machine

| hypothesis | test | result |
|---|---|---|
| the pixel engines use another stream ID | streams 0-14 attached on both DARTs (an experimental overlay) | unchanged, no fault |
| `IOBA` 0 (as t6001, docs/40) | static: H14G never reads it (§3.3) | not used |
| the `venc_dma` power domain is off | live DT: it is the parent of pipe4/pipe5 | on |
| the engines add `vm-base` to 32-bit addresses | source buffers also mapped at IOVA \| 0x800000000 | unchanged |
| translation is wrong | SMMU (0x267020000) dump before and after a frame, against the domain's IOVA→PA table | the SMMU's cache filled with **correct** translations of our recon, LowResRef, SrcNeighbor and coded pages |

The last one moved the search from memory to the firmware: the pixel path
translated our addresses correctly, so the source reader was being told to
read nothing.

### 5.3 The firmware diff

H14G and H13S both carry symbols, so the builds can be compared function by
function. 179 functions changed size; on the source path,
`CDMAController::ConfigPipeRdDMA` grew from 0x3e0 to 0x4d4 bytes. The H14G
version moves the source-reader block to DPE+0x1120010 with 64-bit
addresses, adds registers fed from new host fields next to `src_mode`
(wire 0xFEC3 u8, 0xFEC4 u16, 0xFEC8 u32, read in `InitEncodingParameters`
at 0x4ecfc-0x4ed34; `src_mode` itself is now edge replication, see
`CAVECommonController::CalcProgrammableEdgeReplication`), and **writes
PICMGMT +0x964/+0x968 (17-bit each) to DPE+0x112003c/+0x1120040, plus scaled
copies to +0x11200bc/+0x11200c0, on the linear-input arm**. H13S writes them
only on the compressed arm (docs/85 §1.2: "+0x964 ... compressed input
only"), which is why the driver never sent them. macOS sends +0x964 on every
frame (docs/85 §1.2, kext `0xeb091c`, from FrameInfo+0xA4C).
`CHEVCController::setPipe4PFrame` gained the same two reads.

### 5.4 The fix

Process now carries the source picture's **visible** width and height at
PICMGMT +0x964/+0x968 when the row says `src_dims` (t8112). With 1280x720
there, the I_PCM frame carried the source ramp and every test in the status
table passed. The 1080-line crop in a 1088-line buffer is encoded correctly
with 1080 (the hardware replicates the bottom edge), so the visible size is
the right one. `session_src_dims=` overrides it (0 = the SoC's default,
1 = visible, 2 = MB-aligned, 3 = not sent). The other new fields stay 0;
whether macOS sets them for an NV12 source is [U] (the M2 user-space encoder
was not examined; `tools/fetch_userspace.py` can fetch it), and nothing
measured needs them.

The M1 builds ignore the field for linear input, so sending it there would be
harmless, but it is sent only where tested.

## 9. The PMP and the speed vote

On t6000/t6001 the encoder idles at a low clock until a vote to the PMP
raises it (docs/75, docs/87 §6: ~3x). On t8112 the same mechanics map, and
work, but buy nothing.

**Mapping** (`tools/pmp_ptd_map.py`, now per SoC; controls C1-C4 pass on
both j473 and j314s, and j314s reproduces its row exactly): VENC_SYS PS
0x23b700440; Asahi's t8112 pmp-report offsets 0xa00/0x10500/0xa40, derived
independently from the ADT; PTD read base pmgr reg[39] = 0x23b3c0000
(`pmp_report@23b3c0000`, t600x: reg[41]); soc-device #11 "AVE", DVFS slot 7,
entry 175 (write 0x23b3d0578, read 0x23b3c0af0); PMP/PMS_SRAM PS
0x23b700410; perf block 1 at 0x23b758000. The report entry is `report@9`
(`test/ave-overlay-pmp-venc-t8112.dts`; `pmp_venc=1` now picks the entry by
path and label). These are in the t8112 row.

**The vote is different on t8112.** The VENC pseudo-devices are
`VENC-AVE-VNOM`/`-VMAX`, levels 1 and 2 in perf domain **1**, which on
t8112 is the AP-managed `SOC` domain (ADT `perf-domains`; t600x's VENC
votes are in 32 `PMP-SOC` and 33 `PMP-FAB0`, which only the PMP acts on).
`_pmpWriteDashBoardSetVirtualDeviceState` is the same code as on t6001 and
puts a domain-1 level in the message's low field, so macOS's dashboard
message is `0x2000000000000002`. But because the domain is ≤ 31, macOS also
takes the AP path: `AppleT8110PMGR::setPerfState(1, level)` writes the low
nibble of PMGR ClkGen-SOC +0x58000 (RegMap 63 = ADT pmgr reg[2]) =
**0x23b058000**. That register reads `0x333` (state 3 of 4) with nothing
running and the PMP off, so the SoC is already above what VENC would ask.

**The PMP on t8112.** Enabling it (the asahi-fleet-kernel DTB fixup, now
with t8112's consumers; `--check` passes against a `-DAPPLE_USE_PMP` build)
made m1n1 start it, and its firmware **crashed** ~80 ms into its boot with an
SError at 0x26b910000, inside the ANE, which Linux had powered off. With
`ane_sys` held on (`apple,always-on`) it logged "PMP started", the report
entry acknowledged, and the vote was written and read back. Measured, H.264
fixed QP, 60 frames:

| configuration | 720p | 1080p |
|---|---|---|
| stock (no PMP, ANE off) | **3.2 ms** | **5.8-6.4 ms** |
| ANE held on, no PMP | 3.8 ms | 6.9 ms |
| PMP running, no report / report / vote 2 / vote 3 | 4.9 ms | 9.5-9.6 ms (all four) |

So on the M2 the encoder is fastest with the stock device tree: the PMP
lowers it and no dashboard vote restores it (the AP-side SoC state is
already at its top). The driver keeps the t8112 PMP fields, so
`pmp_report=1 pmp_vote=0x2000000000000002` works mechanically on a
PMP-enabled DT, but nothing should set them.

## 10. Open
- **Placement on other j473s and M2 machines.** Taken from one machine; the
  driver checks RVBAR and the DATA literal before using it, and refuses on a
  mismatch.
- **The other new source fields** (0xFEC3/0xFEC4/0xFEC8) and `src_mode` as
  edge replication: zero works for whole NV12/P010 frames; what macOS sends
  is [U].
- **M2 Pro/Max** (`t6020`/`t6021`): not looked at.
