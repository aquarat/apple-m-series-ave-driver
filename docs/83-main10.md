# 83. HEVC Main 10

**Status (2026-09-27):** a plan from host analysis of the 13.5 kext and
firmware, being run step by step (docs/53 "m0h, m1"). **m1 passes**: NV12
in, Main 10 out, four frames, decodes as `yuv420p10le`. Next: m2, P010
input.

Host-only static analysis. **Nothing here was run on hardware**, and nothing in
the repo was changed. Conventions follow docs/77: fw VAs are 13.5 image VAs
(file = VA + 0x4000). Kext VAs are 13.5 kernelcache VAs. User-space (US) VAs
are in `AppleVideoEncoder` 13.5, with `__TEXT` at 0. "wire" is a byte offset
in the command. VP = wire − 0x60. Labels: **[C]** read from an instruction or
data at the cited VA, **[I]** inferred (the chain is given), **[U]** unknown.

Baseline on this host: `abi_selftest` PASS 1643/0 and `session_selftest`
255/0, both built and run as they are today.

## 1. Input format: what the firmware does, step by step

```
IEP 0x82b10  (x26 = VP+0xF770 → wire = 0xF7D0 + imm; x27 = ctrl+0x23FC4; x28 = ctrl+0xA8C)
  0x832b4  ldr  w9,[x26,#1360]      wire 0xFD20 input_bitdepth
  0x832b8  strb w9,[x28,#1950]      → ctrl+0x122A (u8)
  0x8324c..0x83268  pix_pck (0xFCE8) → [x27,#41] as a bool; forced 0 if wire 0xFD7C ≠ 0
  0x83324  ldr  w9,[x26,#1764]      wire 0xFEB4 → [x27,#380]
  0x83658..0x83680 fmt = bits[4:2]; 4 → SPS chroma_format_idc; else assert fmt ≥ SPS cf (:5118)
  0x83acc  ldr  w8,[SPS,#616]       bit_depth_luma_minus8
  0x83ad8  csel 8/10 → strb ctrl+0x122B
  0x83b20..0x83b34  6·luma_m8 → ctrl+0x122C (QpBdOffset)
  0x83dd0  switch(input chroma fmt) via 0x863fc:
     cf1 (0x83e2c): in==8 → 20; in==10 → 21; else → 26          (enc depth only picks the arm)
     cf0 → 20/21/26 (0x100), cf2 → 18/19/25 (0x200), cf3 → 22/23/27 (0x300), cf4 → assert :5263
  0x83fec  str → ctrl+0xA88
setPipe 0x70778
  0x72730..0x7274c  DPE+0x2000C and +0x2008C = (ctrl+0x23FED<<16) | (ctrl+0xA88<<8)
  0x72094..0x720e0  DPE+0x20000 = 0x80034045 | (input_compressed<<1); stride from PICMGMT+0x8C8 or +0x918
setLRME 0x6a7fc
  0x6c024..0x6c04c  DPE+0x2010C = (pix_pck<<16) | (bScaledSrc<<17) | ([x27,#460]<<8)
```

- The driver's `wr32(&w, hl->input_bitdepth, 8)` (`ave_cmd.c:890`) is load-bearing. 0 would give code 26.
- **The driver already logs `DPE+0x2000C`** after every self-test frame (`ave_session.c:3858`–`3869`, "fmt +0x0C"). 8-bit NV12 should read `0x00001400`, and 10-bit input `0x00001500`. That is a free check that the code reached the register, and it adds no new register reads.
- "10bit content is not supported" (string fw `0xc6166`) is referenced only at `0x540f0`, in AVC setPipe. HEVC has no such line. **[C]**
- macOS US validates `input_bitdepth ∈ {8, 10}` (US `0x71c34`–`0x71c44`, assert string US `0xf1695`), independently of the profile. Where US sets 10 was not found **[U]**. The defaults write 8 (`0x6ced0`–`0x6ced8`: `0xffff0008ffffffff` at VP+0xFCBC).

**Compressed 10-bit input** (`&xv0`/`&xf0`) goes through PICMGMT+0x6F3 and the Interchange geometry (docs/12 §1.4: 32×32 luma tiles at 0x500 bytes, 16×16 chroma tiles at 0x280 bytes, for non-8-bit). No Linux producer makes it, so it is out of scope.

## 4. Implementation (host code; each item pinned by a self-test)

**`driver/ave_cmd.h`**
- `struct ave_hevc_session`: add `u8 bit_depth;` (8 | 10, SPS; 10 ⇒ profile 2) and `u8 input_bitdepth;` (8 | 10, wire 0xFD20).

**`driver/ave_cmd.c`**
- `ave_hevc_ptl()`: take a profile. For 2, write compat[2] only.
- `ave_cmd_build_start_hevc()`: refuse depths outside {8, 10}. Write `hl->input_bitdepth = h->input_bitdepth` (replacing the literal 8 at `:890`). Write `sps + p->bit_depth_luma_m8/chroma_m8 = bit_depth − 8`, both equal.
- `ave_hevc_verify()`: re-read 0x248F4 == 0x248F8 ∈ {0, 2}, 0xFD20 ∈ {8, 10}, and profile 2 ⇔ depth 2.

**`driver/ave_session.c`**
- Parameters: `session_hevc_bitdepth` (8/10) and `session_src_bitdepth` (8/10), both default 8. Also `session_flat_luma10` (0..1023, 0 = ramp).
- `ave_recon_planes(w, h, bd)`: luma and chroma `×bd/8`. The slot layout must match setRefPointers exactly: UV_MSB = Y_MSB + luma. This is the one place where a mistake corrupts silently (§6 R1).
- `ave_session_hevc_entropy_size(..., bd)` ×2. `ave_session_coded_size(..., bd)` ×5/4, with TranscodedData following it.
- Source fill for P010: `u16 le`, value `v10 << 6`, where v10 = `64 + x·876/w + ((y/16)&7)·4`, Cb 512, Cr `512 + (((x/32)&15) − 8)·4`, rows padded to stride. The fill uses every 10-bit code, so the two LSBs vary. Allocate `2·stride`.
- Log: extend the HEVC_INIT line with "Main10 bd %u in %u (fmt code expect %u)".

**`driver/ave_v4l2.c`**
- `ENUM_FMT(OUTPUT)`: index 1 = `V4L2_PIX_FMT_P010`, only while CAPTURE is HEVC and 10-bit is supported. The stateful-encoder spec lists only the OUTPUT formats valid for the current CAPTURE format.
- `ave_fill_out_fmt`: P010 → `bytesperline = 2·ALIGN(w,64)`, `sizeimage = ave_out_size(HEVC, bpl, h)`. For H.264, try_fmt turns P010 into NV12.
- `S_FMT(CAPTURE)` = H264 while OUTPUT = P010: reset OUTPUT to NV12, or `-EBUSY` with buffers, as the codec-change rule does today.
- `HEVC_PROFILE` menu: mask `~(BIT(MAIN)|BIT(MAIN_10))`.
- Profile rule: OUTPUT P010 ⇒ MAIN_10. The control is updated (ffmpeg never sets it). MAIN_10 with NV12 is allowed: firmware code 20, 8-bit in, 10-bit coded (§0 1d). MAIN with P010 is refused at STREAMON, because the 10 → 8 path (code 21, 8-bit internal) is never tested before m2.
- `ave_enc_cfg`: add `bit_depth`, `src_bitdepth`. `ENUM_FRAMESIZES` accepts P010.

**Tools (host)**
- `hevc_parse.py --check --main10`: profile 2, compat[2], depth 10/10.
- `ramp_psnr.py` / `check_frame.py --bits 10`: decode `-pix_fmt yuv420p10le`, 16-bit LE samples, peak 1023, and the existing controls.
- `v4l2-test.sh FMT=p010`: the source comes from `ffmpeg … -pix_fmt p010le -f rawvideo`, and the stream is graded on the host.

**Self-tests**
- `abi_selftest`: Main10 pins 0x105D0 = 0x246AC = 2, 0x246B1 = 0, 0x246B2 = 1, 0x248F4 = 0x248F8 = 2, 0xFD20 = 10. Refusals: depth 9/12, luma ≠ chroma, 0xFD20 ∉ {8, 10}, profile 2 with depth 8. Control: `bit_depth = 8, src = 8` must give **byte-identical** INIT/ENCODE to today's.
- `session_selftest`: 720p 10-bit recon {1 177 600, 588 800, 65 536, 16 384}, entropy 2 211 840, coded 1 728 512, TranscodedData 864 256, and the P010 fill (sample 0 of row 0 = `64<<6`).

## 5. Hardware test plan (m-series, docs/53 style; for the lead)

Each run is one boot and one variable. Repeat before believing: every "yes" gets an identical `…r` rerun. Grade on the **host** (Fedora on the target has no HEVC decoder). Host ffmpeg 7.1.1 decodes Main 10: `ffmpeg -i f.h265 -pix_fmt yuv420p10le`. Base line, as h3h/h4b:

```
B="OVERLAY=4 OVERLAY_WAIT=0 HOLD=5"
P="session_selftest=1 session_codec=1 session_qp=30 session_dbg=0x20 session_frame=1"
```

**m0 (host only).** Build the driver. Both self-tests pass, including the byte-identical 8-bit control. Without that, no reboot.

**m0h: control on the new build.** `tools/lab-run.sh m0h "$B" $P`, which is h2c's parameters. *Expect* h2c's results exactly: 1207 bytes, Y 50.96 dB, and `fmt +0x0C 0x00001400` in the log. *No:* the refactor changed 8-bit bytes. Stop and diff the commands.

**m1: 10-bit coding, 8-bit input** (NV12 ramp → Main 10). `… $P session_hevc_bitdepth=10`.
- *For:* SPS/PTL fields, the internal depth, recon ×1.25, entropy ×2 and coded ×1.25, with the input path unchanged (code 20).
- *Yes:*
  - `INIT_DONE 0xEE0000`;
  - fw log `HEVC PIPE:: sps->bit_depth_luma_minus8 2 … chroma 2` and `BitDepth.all 22`;
  - `fmt +0x0C 0x00001400` (still 20);
  - `hevc_parse --check --main10` passes;
  - the stream decodes as yuv420p10le;
  - Y PSNR against `src8<<2` (10-bit peak) ≳ 45 dB;
  - the slice QP in the header is **18** ([I] §0 2d; **30** would refute the QP′ reading, with no harm done).
- *No shapes:*
  - `0xEE0005` / an assert at INIT: a misplaced PTL/SPS offset (parse the param sets, no reboot needed);
  - pipe hang at frame 0 with recon progress 0: the recon slot is too small, or the entropy is (compare the "recon planes" log line with §3);
  - decodes but chroma is shifted or garbage while luma is good: **UV_MSB offset** (R1);
  - decodes at about ¼ or ×4 amplitude: the SPS says 10 and the pipe coded 8 (or the reverse). Check `BitDepth.all`;
  - decode error in the slice data: the transcoder depth nibble does not match the SPS (`0x75bcc`).

**m2: 10-bit input, 8-bit coding** (P010 flat → Main). `… $P session_src_bitdepth=10 session_flat_luma10=800`.
- *For:* the input fetch alone (code 21) against the known-good 8-bit pipeline, and the sample alignment. 800 = 0x320 is stored as 0xC800.
- *Yes:* `fmt +0x0C 0x00001500`; the decoded 8-bit luma is ≈ **200** (800/4 ± QP noise), flat.
- *No shapes, and what each names:*
  - ≈ 0/16 (black): the fetcher takes the **low** 10 bits (0xC800 & 0x3FF = 0), which is LSB-aligned. The fix is a host shift, and V4L2 then needs a different fourcc;
  - alternating columns ≈ 0 and ≈ 200: an 8-bit fetch (code not 21; check that wire 0xFD20 reached the log line);
  - a 3-periodic pattern (e.g. 512/384/352 in 10-bit terms): a **packed** fetch (p420). Go to m2b;
  - `fmt +0x0C` still `0x1400`: 0xFD20 did not reach the IEP (layout);
  - hang: a source DMA stall. The netconsole tail and docs/59–61 signatures apply.
- *Repeat* m2r. Then run **m2-ramp** (the same run with the ramp, `session_flat_luma10=0`): Y ≥ ~45 dB against `src10>>2`.

**m2b (only if m2 looks packed or wrong):** m2 plus `session_src_cfg=1` (pix_pck = 1, macOS's value). *Yes:* m2's ≈ 200. *No:* the same picture, so pix_pck is not the packing selector. Record it and stop the 10-bit input work there. The x420/p420 selector is then elsewhere **[U]**.

**m3: both** (P010 ramp → Main 10). `… $P session_src_bitdepth=10 session_hevc_bitdepth=10`.
- *Yes:* `fmt 0x1500`, `BitDepth.all 22`; Y PSNR (10-bit peak) against the P010 source ≳ 48 dB. Use `ffmpeg -lavfi psnr` on yuv420p10le, and `ramp_psnr.py --bits 10`.
- *No:* m1 and m2 pass while m3 fails. That is an interaction: code 21 with the 10-bit internal path. Diff the logs.

**m4: P frames.** m3 + `session_frames=4` (IdrPeriod becomes 30 by itself, docs/77 §16), with the SrcNbr/LowResRef ×2 hedge on.
- *Yes:* frames 1–3 are NAL 1 P; Y close to the IDR's; no `:13296/13297` assert.
- *No shapes:*
  - `:13296/13297`: `sRef.Y_L0_LSB` is 0 or unaligned (the ref arrays lack the DPB second u64);
  - a PIPE HANG like h3 (docs/77 §17 diag dumps apply);
  - chroma drift over frames 1–3 with good luma: **R1**, the chroma recon plane offset (m1 is the IDR-only control).
- **m4b:** the same without the hedge. It must match m4.

**m5: V4L2, v4l2-ctl** (new code). Commands:

```
ffmpeg -f lavfi -i testsrc2=size=1280x720:rate=30 -frames:v 60 -pix_fmt p010le -f rawvideo in.p010
v4l2-ctl --set-fmt-video-out=width=1280,height=720,pixelformat=P010 --set-fmt-video=pixelformat=HEVC
```

stream 60 frames at fixed QP.
- *Yes:*
  - `--list-formats-out` shows P010 only with HEVC selected;
  - `HEVC_PROFILE` reads MAIN_10 after S_FMT(P010);
  - 60 frames, 1 I + 59 P;
  - host PSNR ≈ m3's;
  - `v4l2-compliance -s` still 54/54 on the H.264 default.
- *No:* a failure where m3 passed is the single-buffer layout (chroma at `bpl·h`), as docs/77 §19.5.3.

**m6: sizes.** m5 at 1920×1088 with crop 1080, then 3840×2160 (30 frames). *No* at 4K only: a size-dependent buffer (entropy flag or SrcNbr). Rerun the self-test at that size.

**m7: GStreamer.**

```
gst-launch-1.0 videotestsrc num-buffers=60 ! video/x-raw,format=P010_10LE,width=1280,height=720 ! v4l2h265enc ! video/x-h265,profile=main-10 ! h265parse ! filesink
```

*Yes:* caps negotiate with no conversion element needed, and the stream decodes as Main 10.

**m8: rate control at 10 bits** (GStreamer or v4l2-ctl with a bitrate; ffmpeg cannot send P010 unpatched). *No:* rate far off target, or `XCODE HANG`. Possible causes: QP′ range and RC clamps (0xFF88/0xFF8C) in the 10-bit domain [U], or docs/77 §20's pairing.

**m9: regression.** h4's `v4l2-test.sh 60 ctl` for HEVC Main and H.264. The sizes must be byte-identical to f80/h4.

## 6. Risks

| # | risk | why | guard |
|---|---|---|---|
| R1 | **Chroma recon at the wrong offset** | the firmware computes UV_MSB = Y_MSB + luma×bd/8 itself (`0x2c324`, ctor `0x2e424`). An 8-bit-sized slot puts chroma in the wrong place with **no assert**: bad chroma in P frames, and overrun into the next slot | size the slots from §3; session_selftest pins; m1 (IDR) vs m4 (P) chroma |
| R2 | Entropy too small (×2) | no size assert beyond ≠ 0 (`:14199/14200`); overflow is silent corruption or a hang (the AVC entropy saga, docs/61/62) | ×2 per `…ea5c50` |
| R3 | Coded / TranscodedData too small | intra 10-bit frames are ~25% larger. The transcoders write the TranscodedData pair of fixed size (ctrl+0x20A0) and the merge memcpy's into coded (`0x7e4f8`–`0x7e61c`, docs/77 §14). Overflow → data abort, like h2b's `0x7F578` | ×5/4; first runs at QP 30 |
| R4 | Wrong x420/p420/alignment | §0 1e [U]; a wrong interpretation looks like a working encoder with a wrong picture (the F17 trap) | m2's flat 800 with three distinct failure pictures; `fmt +0x0C` readback |
| R5 | wire 0xFD20 ∉ {8, 10} or luma_m8 ∉ {0, 2} | code 26 (unknown layout) or an SPS that disagrees with the pipe | builder refusals and `ave_hevc_verify` |
| R6 | 0xFEB4 changed while touching input format | `:5118` assert + spin at INIT (docs/77 §7) | leave 16; abi pin |
| R7 | New 10-bit-only asserts | `:13296/13297`, `:13521/13522` (ref LSB ≠ 0, % 64), only with luma_m8 ≠ 0 | session_lsb stays on; the builder already refuses LSB = 0 |
| R8 | §15's entry-point scan | S+0x54C/0x550 must stay 0xFFFFFFFF. 10-bit does not change WPP rows | untouched; abi pin exists |
| R9 | §16 IdrPeriod | P runs need 30 | unchanged logic |
| R10 | §20 `cu_qp_delta` / QP domain | slice QP is QP − 12 at 10 bits (`0x66fdc`); RC's QP window (0xFF88/0xFF8C, SoftMaxQP) may need +12 [U]. Stay at fixed QP until m8 | m1's slice-QP check; m8 last |
| R11 | Source over-read | the HEVC fetcher may read whole 64-row CTB pairs (docs/77 §19.3). With a doubled stride, the V4L2 `sizeimage` must keep the `ALIGN(h,64)` chroma slack | same formula, bpl doubled |
| R12 | LRME/low-res fed 10-bit | the third reader gets code 21 (`0x6c024`). The LowResRef size has no depth term; if low-res planes were 16-bit they would overflow [U] | m4 hedge, then m4b |
| R13 | Tool false negatives | `hevc_parse --check` asserts profile 1 / 8-bit (`hevc_parse.py:564,570`); the PSNR tools assume peak 255 and 8-bit decode (`ramp_psnr.py:35,54`; `check_frame.py:37,94`) | `--main10` / `--bits 10` before m1 |
| R14 | VUI/colour | P010 sources are often BT.2020/PQ. The driver sends no VUI, and the firmware's VUI writer is non-conformant (docs/77 §2.3), so HDR signalling is a separate item | out of scope; log colorspace |
