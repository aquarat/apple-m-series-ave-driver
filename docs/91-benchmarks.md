# 91. Benchmarks: M1 Pro and M2

*Speed, compression and energy of the AVE encoder on the two machines it
has been measured on, with charts. 2026-10-03.*

Machines: an M1 Pro (t6000, MacBookPro18,3, docs/87) and an M2 Mac mini
(t8112, j473, docs/90), both Fedora Asahi Remix 44, kernel 7.1.13 (16K),
macOS 13.5 stub firmware. The charts are generated by `bench/plots.py`
from the CSVs in `bench/`; rerun it after adding results.

## 1. Speed

![encode speed](img/speed.svg)

Per-frame hardware time from the driver's `enc:` line, one stream, fixed
QP, `testsrc2` source (`bench/speed/run.sh`; the M1 Pro rows are docs/87
§5 t1/t3, H.264, 60 frames):

| | 720p | 1080p | 2160p |
|---|---|---|---|
| M1 Pro, H.264, no PMP vote | 7.91 ms (126 fps) | 15.53 ms (64 fps) | 55.5 ms (18 fps) |
| M1 Pro, H.264, PMP vote | 2.87 ms (348 fps) | 5.15 ms (194 fps) | 18.3 ms (55 fps) |
| M2, H.264 | 3.22 ms (310 fps) | 6.35 ms (158 fps) | 23.6 ms (42 fps) |
| M2, HEVC | 4.32 ms (232 fps) | 8.50 ms (118 fps) | 31.1 ms (32 fps) |

The M1 Pro needs the PMP vote (docs/87 §6) for its speed; the M2 runs at
full speed without it, and is slower with the PMP running (docs/90 §9).
HEVC costs the M2 ~1.3x the H.264 time. The M1 Pro's HEVC speed was not
measured here: its encoder is in production use.

## 2. Compression: the same on both

![rate-distortion](img/rd-vmaf.svg)

![per device](img/rd-per-device.svg)

The bench of docs/88 (`bench/hevc-efficiency`, five Xiph derf 1080p50
clips, 200 frames each, VMAF 0.6.1 / PSNR / SSIM) was rerun on the M2 for
AVE's two fixed-QP modes, 8-bit (`ave-cqp`, QP 22-38) and Main 10 from a
P010 source (`ave-cqp-main10`, QP 34-50), with the M1 Pro's QP ladders
(`results-m2.csv`). **All 50 points are identical to the M1 Pro's** in
bitrate, PSNR-Y, PSNR, SSIM and VMAF, to every printed digit: BD-rate M2 vs
M1 Pro is 0.00 % on every clip, in both modes and both metrics. The two
SoCs' encoders produce the same streams from the same input and settings;
only their speed and power differ. So docs/88's comparison with x265 holds
for the M2 as well:

![BD-rate](img/bdrate.svg)

AVE HEVC needs ~20 % (VMAF) / ~21 % (PSNR-Y) more bitrate than x265
`--preset medium` at equal quality on these clips (docs/88 has the slow
preset, bitrate mode and the camera clips).

## 3. Energy

![energy](img/energy.svg)

Energy per frame above idle, whole machine (SMC "Total System Power",
`bench/hevc-efficiency/power.py`, `crowd_run` 1080p50 at 8 Mbit/s through
ffmpeg's `hevc_v4l2m2m`, 60 s phases):

| | idle | over idle while encoding | fps | per frame |
|---|---|---|---|---|
| M1 Pro, AVE | 6.1 W | 3.6 W | 117 | 31 mJ |
| M2, AVE | 3.1 W | 0.9 W | 87 | **11 mJ** |
| M1 Pro, x265 `ultrafast` / `medium` | | 23.8 / 24.6 W | 73 / 33 | 328 / 759 mJ |

(`power.log`, `power-m2.log`.) The fps here is ffmpeg's whole loop, not the
hardware time of §1: with the bitrate-mode path the CPU side of each frame
adds up, and the M2 does that part slower. Against x265 `medium` on the M1
Pro's CPU, AVE uses ~25x (M1 Pro) to ~70x (M2) less energy per frame.

## 4. Reproduce

```sh
# speed (target, driver loaded)
sudo bench/speed/run.sh "M2" 120 >> bench/speed/results.csv
# compression: bench/hevc-efficiency/README.md, then on the target
RESULTS=results-m2.csv ENCODERS=ave-cqp,ave-cqp-main10 python3 bench.py run \
    crowd_run park_joy ducks_take_off in_to_tree old_town_cross
# energy
POWER_TESTS=crowd_run:8000 POWER_ENCS=ave python3 power.py | tee power-m2.log
# charts (host)
.venv/bin/python bench/plots.py
```

## 5. Can it compress better?

Yes, with B frames: one B frame per P at B QP +3 needs 7.6 % (VMAF) /
9.7 % (PSNR-Y) less bitrate than P frames only, at the same hardware time
per frame; the gap to x265 `medium` drops from 20 % to 11 % (docs/96). A
separate P-frame QP buys 1.5-2 % (docs/92), a second reference 0.1-0.6 %
(docs/94). The firmware's 2-pass mode works through the driver's lab path
but is worse than its 1-pass VBR (+5 % VMAF, +11 % PSNR-Y BD-rate, docs/95
§11), so it is not a lever yet.
