# Incident: hard SoC hang during the first probe attempt

**2026-09-07, M1 Max (j314c), Fedora Asahi 7.1.6-400.**

The machine went down hard while attempting the first driver probe. No data was
lost and nothing persists, but the risk assessment that led to the attempt was
wrong, and the way it was wrong is worth recording.

## What happened

1. `apple-ave.ko` was built and loaded. It bound to nothing, as expected — the
   base device tree has no `apple,ave` node.
2. To give it something to bind to, a device-tree overlay was written adding
   **both** an `ave0` node and a `dart_ave0` IOMMU node, plus a helper module to
   apply it (this kernel has `CONFIG_OF_OVERLAY=y` but no configfs interface).
3. The first apply was rejected — `dtc -@` emits a `__symbols__` node the live
   tree does not have (`init_overlay_changeset() failed, ret = -22`).
4. The overlay was rebuilt without `-@` and re-applied. Shortly after, the
   machine stopped.

## Evidence

- **PMU record: `1 boot error(s) and 0 panic(s)`.** Zero panics is the important
  part: this was not a kernel software fault. It was an unclean hard stop.
- No oops, no `BUG:`, no stack trace, no pstore entry.
- The last journal line is an ordinary `sudo` session opening and closing
  normally, then nothing.

That signature — instant stop, nothing logged, no panic, PMU boot error — is
what an **SoC-level hang** looks like: a CPU wedged with interrupts off, reset
by the PMU watchdog.

## Correction — the first root-cause hypothesis was wrong

The original version of this document blamed the DART's power domain: the
overlay gave `dart_ave0` `power-domains = <0x1d>` (`venc_sys`) while the ADT
says `dart-ave0` uses gate 508 `VENC-DART`, so the theory was that
`apple-dart` wrote to an unpowered block.

**Checked, and it does not hold.** The ADT's PMGR device table splits into two
classes: real power gates carry a non-zero `psreg`, while `psreg == 0` entries
are performance/voltage/dependency pseudo-devices. `VENC-DART` (508) is one of
the latter, and its parent is `VENC_SYS` (294, `psreg=10 psidx=22`) — which is
exactly Linux's `venc_sys`. The overlay's power reference was **correct**.

The same check clarifies the domain model generally: of the eleven gates `ave0`
declares, only `VENC_DMA/PIPE4/PIPE5/ME0/ME1` (300–304) are real gates. The
other six are pseudo-devices. Together with `VENC_SYS` (294) that is exactly the
six domains Linux models — so the six-domain model in `driver/ave_hw.h` is
right, for a better reason than was originally documented.

**The cause is therefore unknown.** Recorded that way rather than replaced with
a second guess.

## Leading suspect (unproven)

Device probe is asynchronous. `insmod` returning cleanly and the shell session
closing does **not** mean the overlay was safe; the probe ran afterwards.

The DART remains the component most likely to be at fault, because it is the
only one that *writes* registers on probe — `apple-ave` merely `ioremap`s and
then fails at firmware adoption without touching hardware.

The concrete discrepancy: **every existing `apple,t6000-dart` node in the live
device tree has exactly one `reg` range. The overlay gave `dart_ave0` four**,
transcribed from the ADT, which declares four banks at `0x20D040000`,
`0x20D030000`, `0x20D020000` and `0x20D044000`. That suggests AVE's DART is a
multi-instance device, and presenting it to a driver written for a single
instance is a plausible way to write to the wrong place.

Unproven. It is a lead, not a diagnosis.

## Where the risk assessment went wrong

[23-empirical-bringup.md](23-empirical-bringup.md) argued the blast radius was
small: the DART contains bad addresses, iBoot owns the firmware, so the worst
case is a wedged coprocessor needing a reboot. **That reasoning was sound for
the coprocessor and was then wrongly extended to the whole experiment.**

The specific errors:

1. **The DART is the safety net, so standing up a new DART is not a contained
   act.** The containment argument assumed a *working, correctly powered* DART.
   Creating one from an inferred power-domain reference is a different and much
   larger risk than anything the AVE driver itself does.
2. **"Probe will fail cleanly at firmware adoption" only covered `apple-ave`.**
   The overlay bound two drivers. The other one was never risk-assessed.
3. **Asynchronous probe was not accounted for.** A clean `insmod` return was
   treated as evidence the step had completed safely.
4. **A daily-driver laptop with no serial console was the wrong venue.** A hang
   with no console is a black box: it destroys exactly the information needed to
   understand it.

## What this changes

The machine is experimental and a reboot is cheap, so the constraint is not
"never crash" — it is **never crash blind, and never crash persistently**.

Crashes do not persist: modules are `insmod`-ed rather than installed, overlays
are RAM-only, and nothing is written to `/boot`. Verified after this reboot.
The one real hazard from repeated hard resets is filesystem damage, so `sync`
before each attempt.

Crashing blind is the part that has to change. A serial console is the best
answer but is weeks away; the substitutes available today are:

1. **netconsole** — ships the kernel log to another host over the LAN. Needs no
   special hardware. Caveats: this machine is on wifi, so the network stack is
   itself in the blast radius, and a truly instantaneous hang may not flush the
   last messages. It still converts most hangs from silent to diagnosable.
2. **Drop the DART from the experiment.** It is the only component that writes
   registers on probe and it is the leading suspect. `apple-ave` does not need
   an IOMMU until it does DMA, which is several steps away.
3. **One question per boot.** With coarse instrumentation, each attempt should
   be designed so that surviving or hanging is itself the answer.

Revised order for a first probe attempt:

1. Set up netconsole to another host on the LAN and confirm it carries `dmesg`.
2. Bring up **only** the AVE node — no DART, no `iommus` property.
3. Instrument `ave_probe()` with a `printk` before and after every step, so the
   last line received names the step that hung.
4. Expect probe to fail at firmware adoption, and treat reaching that failure as
   success.
5. Only then reintroduce the DART, as its own separate experiment, and resolve
   the four-versus-one `reg` range question first.

## State afterwards

Nothing persists. The modules were `insmod`-ed, never installed to
`/lib/modules`; there are no `modules-load.d` or `modprobe.d` entries, no
`.dtbo` in `/boot`, and device-tree overlays are RAM-only. A reboot fully clears
it, which is what happened.

The test scaffolding is kept in `test/` with this document referenced from it,
so the next person does not repeat the attempt unaware.
